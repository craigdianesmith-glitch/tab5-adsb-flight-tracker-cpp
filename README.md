# Overhead (C++)

A C++ rewrite of [Overhead](https://github.com/craigdianesmith-glitch/tab5-adsb-flight-tracker-micropython), a live ADS-B flight tracker for the [M5Stack Tab5](https://docs.m5stack.com/en/core/Tab5). Built on PlatformIO + Arduino + M5Unified/M5GFX (no LVGL), with genuine multithreading: the network fetch runs on its own FreeRTOS task pinned to core 0, so the UI never blocks - the thing that wasn't possible on the MicroPython version, where sockets couldn't be created from a secondary thread at all.

**New in 1.5: the flight in 3D.** Follow any aircraft and the Tab5 flies it live in 3D - at its airport's real terminals, taxiways, stands and tower, from the OpenStreetMap airfield pack, under the real sun, with the sound of its engines - drawn by a software 3D engine written for the ESP32-P4, which has no 3D hardware: prepared on one core and drawn in bands on both, in the chip's own fast memory, its inner loops in the P4's PIE vector instructions, at 20 to 70 frames a second. Recorded flights replay in 3D too. We know of no other flight tracker that does this on a microcontroller. See [The 3D view](#the-3d-view).

**New in 1.5.1: the land in 3D.** With the ground pack on the card, the 3D view draws the land at its real height - the hills and mountains of the UK and Ireland, from any height, at an airfield, on the approach or in the cruise - in the colours of what covers it, marched over the land's heights in hand-written RISC-V assembly. For anywhere else, `tools/make_ground_pack.py` makes the pack on a computer, for a country, a region or the land round a town. See [The ground pack](#the-ground-pack).

## Hardware

- M5Stack Tab5 (5" 1280x720 touchscreen, ESP32-P4 + ESP32-C6)
- A microSD card, FAT32 - optional: for recordings, replays, video export and sharing, and the 3D view's airfield and ground packs

## Toolchain

Tab5's ESP32-P4 isn't supported by mainline PlatformIO yet - this uses the community [`pioarduino`](https://github.com/pioarduino/platform-espressif32) fork of the espressif32 platform (see `platformio.ini`).

```
pip install platformio
```

## Setup

1. Copy `include/secrets.h.example` to `include/secrets.h` (it is gitignored). Filling in WiFi credentials there is optional: a build left with the placeholder opens the WiFi screen on boot and takes a network on-screen instead, which is how a device flashed from a released image is expected to be set up. Credentials compiled in here are only ever a fallback for a device that has never been given one that way.
2. Build and flash:
   ```
   pio run -t upload --upload-port /dev/ttyACM0
   ```
   An image to publish is built with `pio run -e release` instead, into `.pio/build/release/firmware.bin`: the same firmware without `include/secrets.h`, so the credentials of whoever built it never reach it, and it opens the WiFi screen on first boot. The libraries are pinned to the commits it was tested against. The image M5Burner flashes is the merged one beside it, `firmware.factory.bin` - bootloader, partition table, a blank settings area and the app, written at offset 0x0.
3. Watch serial output at 115200 baud for boot/WiFi diagnostics if anything looks wrong. Once a minute it also logs a `[perf]` line: how long the radar and zoom took to draw - split into the parts that don't move from frame to frame, the contacts, and the push to the panel - the longest pass of the main loop, and how much internal RAM is free. Measured on the radar and zoom at Glasgow: about 40-50ms a draw, of which 8ms the scope, airports and runways, 1ms the contacts and 19ms the push - too little in the unmoving parts for caching them to be worth its keeping in step.

## Screenshots

The Tab5 has no screenshot function of its own, but everything on screen is drawn into a landscape canvas in PSRAM before the PPA rotates it onto the panel - so the firmware answers a `##S` on USB serial with that canvas, and `tools/screenshot.py` turns it into a PNG:

```
pip install pyserial pillow
python tools/screenshot.py radar.png
```

It is pixel-exact and the right way up whatever the device's orientation, and takes about three seconds. The UI doesn't take touches while it is sent, so grabbing one every few seconds makes the device feel sluggish; and during a video export, which holds the main loop, the request isn't answered until the export ends. Close any serial monitor first. The script leaves DTR and RTS as the kernel sets them on open: clearing DTR while RTS is still raised is the ESP32's USB-serial reset signal, which is what pyserial's usual `dtr = False` sends. And it checks that the end marker follows the last pixel exactly, retrying if a log line from the poll task landed mid-transfer and shifted the image.

## Notable hardware quirks this project works around

- **WiFi**: Tab5's WiFi lives on a separate ESP32-C6 co-processor reached over SDIO. The generic P4 eval-board pin defaults don't reach it, so `hostedSetPins(12, 13, 11, 10, 9, 8, 15)` must be called before WiFi initializes (see `main.cpp`). M5Unified is supposed to do this automatically in `M5.begin()`, but it's called explicitly here too.
- **Flash partitioning**: the board's default Arduino partition scheme reserves a tiny (~1.3MB) app partition despite 16MB of flash. `partitions_custom.csv` gives the app a single ~14MB partition instead (no OTA needed for this project).
- **HTTPClient's User-Agent**: `HTTPClient::addHeader("User-Agent", ...)` is silently overridden by an internal default (`ESP32HTTPClient`) - use `setUserAgent()` instead. adsb.lol rejects generic User-Agents outright.
- **mbedTLS stack size**: the background poll task needs a considerably larger stack (16KB) than a typical FreeRTOS task, or HTTPS requests fail silently.
- **Speaker startup**: `M5.begin()` configures the Tab5's ES8388 codec and enables its amp, but stops short of starting the I2S output - nothing is audible until `M5.Speaker.begin()` is called as well (see `src/sound.cpp`).
- **H.264 encoder input**: this board's P4 is an early revision (v1.x - the board definition builds against the `esp32p4_es` libraries), and on those the hardware H.264 encoder takes only its own packed YUV 4:2:0 layout (`O_UYY_E_VYY`: odd lines U Y Y, even lines V Y Y), not the RGB565 the canvas holds. The PPA converts into it - see [Video export](#video-export). And `esp_h264_alloc.h` has no `extern "C"` guard, so its allocators don't link from C++; `heap_caps_aligned_calloc` does the same job.
- **Rotated framebuffer**: the panel is physically 720x1280 portrait, so in the landscape orientation this app runs at, every horizontal line of the UI is a *column* in memory. LovyanGFX's rotated `pushSprite` can't memcpy in that case and walks the image pixel by pixel - a full-screen push measures **650ms** on this device. `src/screen.cpp` hands the rotation to the ESP32-P4's PPA (its 2D graphics accelerator) instead; see below.

## Header

The left of the bar says what is being shown, where from, and who it came from - `ADSB Flights - Civilian near GLA   via adsb.lol` - and the right carries the five controls: the filter, replays, radar, mute, and the cog. The airport is the nearest one to the configured location from the same table the radar centres on, and is left off entirely when nothing is within range of it. What is shown follows the filter's kinds: down to the cargo flights it says `Cargo near GLA`, and the radar's title `Radar - CRG`; the military alone, `Military` and `MIL`; two of the three, `Cargo & military` and `CRG+MIL`, or `Civil & military` and `CIV+MIL`. Civil and cargo together are all the civil traffic, and with military as well everything, which keeps the civil name, `Civilian` and `CIV`.

The source is named because it can change on its own: under **Auto** the tracker fails over between providers, and a table quietly being served by the other one should say so rather than leave it to be guessed. It appears once a poll has succeeded, and changing it forces the repaint that draws it.

The controls sit together at the right edge rather than scattered across the bar, which leaves the whole left side to that one line. Muting is a header control rather than a settings one because it is the thing most likely to be wanted in a hurry.

## The table

Seven columns: flight, type, altitude, speed, distance, heading and status. Tap a heading - any but HDG, which way each is pointing being no order - to put the rows in its order - smallest first, and tapped again the other way - with that heading a deeper green and a triangle after its title pointing the way they run; what isn't known, a `?`, goes last either way, and the order is kept across a reboot. Nearest first is where it starts. A row is found by the aircraft's hex rather than its place in the list, so a poll landing between the table being drawn and a tap can't open the wrong one. There are eleven rows; with more aircraft than that, the status line says which are shown at its right - `1-11 of 18 - drag for more` - and a drag up or down the table moves through them a row at a time, tap and hold still working on the rows as they are. That readout has a strip of its own, repainted only when it changes, so the status line's left part - repainted each second as its age ticks over - stays the narrow strip it was.

Altitude is given in feet up to 9999 and as a flight level above that - `FL200` for 20000ft, hundreds of feet as the convention has it. Past ten thousand the exact figure is neither how the altitude gets referred to nor worth the width of five digits, and the column is narrower for it.

Heading is the reported ground track in three digits, `035` rather than `35`, the way a heading is written and spoken. Status carries a drawn icon ahead of its word, so the column reads at a glance without the text having to be parsed.

Widths are fixed rather than measured: the content of each column is known and bounded - eight characters of callsign, four of designator, five of flight level - so there is nothing to be gained from measuring at runtime, and a table whose columns don't move between refreshes is easier to read. They are sized against the widest realistic value in each column, in the table's font: FLIGHT fits eight `W`s, the widest callsign there can be (272px), where it used to be too narrow for `LOG27VQ`; STATUS fits `DESCEND` behind its icon; HDG never holds more than three digits, and had been given room for seven. A value that is still too wide is drawn at a smaller size until it fits, rather than running over the border into the next cell.

A callsign the transponder sent as blank arrives from readsb as a row of `@`s. Those are stripped, and an aircraft left with no callsign - or with no callsign field at all - goes by its registration, `G-ABCD`, where the feed has one, and otherwise by its ICAO hex: `UNKNOWN`, as one with a blank callsign used to show, named nothing.

## Settings

The cog opens a settings screen in two columns - ten controls will not stack down 720px of height, and 1280px of width was going spare:

Its title bar has the version beside the title, and **Display**, **Help** and **About** beside Back. **Display** is a page of its own: the screen's brightness, on a slider that sets it as it moves, 10 to 100%; **dim when untouched** - off, 5, 15 or 30 minutes - after which the screen goes down to an eighth of that, for a desk or a wall at night, coming back as a finger lands, that touch doing nothing else so a tap meant to wake it doesn't press what was under it, and as an alert fires; and the radar's clock: off, in UTC, or in the local time of the UK, central Europe or the mainland United States' four zones, summer time and all - `14:32 BST`, `09:32 EDT`. Until one is picked it keeps the zone home is in, following it to a new location, and UTC where home is in none of them. The zones are worked out by `src/clock_zone.cpp` rather than through the C library's TZ, which stays UTC for the recordings. And under the clock, **replay tracks**: whether a replay, and a video exported from one, draws each aircraft's last ten minutes behind it; on unless switched off. **Help** is two pages on how to use the tracker - the table, radar, airport zoom, following, alerts, recording and settings - and **About** the version, what is on the SD card - the airfield and ground packs, or why the 3D view goes without each and what to do - a disclaimer (for interest only, not for navigation or anything safety depends on; the data can be incomplete or wrong; take-offs, landings and the spoken clearances are simulated) and the credits for the data, voice and libraries. Both are `src/info_screen.cpp`, written as headings, paragraphs and bullets and wrapped and paged to fit when opened, so the words can change without anything being counted.

- **Range** - a slider to 60nm, and with a filter on to 250nm, there being fewer aircraft to show; clearing the filter with the slider up high clamps it back down. What is shown - civil, cargo or military - is the filter's, by kind: there was once a civilian/military switch here, which the filter's Military alone has replaced. A device left in military mode comes up with the filter set to that, and its radius kept. Military aircraft are the ones readsb sets bit 0 of `dbFlags` on.
- **Show flight refresh** - whether cells that changed on the last poll are shaded for a moment (see Rendering below). On by default.
- **Navaids** - whether the radar marks the VORs, DMEs and TACANs in range (see [Radar](#radar)). On by default.
- **Map** - whether the radar has the coasts, lakes and borders under it (see [Radar](#radar)). On by default.
- **Range rings** - whether the radar has its distance rings, inside the outer one. Off by default: the map says where things are, and with the rings off it is drawn a little brighter, having the plot to itself. The airport zoom keeps its rings either way.
- **Data source** - which provider to poll: **Auto**, or one of them pinned. Auto is the default and the reason this control exists - see [Data sources](#data-sources). Pinning is for when you would rather know which one you are looking at than have it chosen for you; a pinned provider's empty answer is reported as it stands, with no second opinion sought.
- **Refresh interval** - how often the sky is refetched, from 5 to 60 seconds in fives, defaulting to 30. The slider is stepped rather than continuous, with a detent mark per position, so it can't be left on a value nobody asked for. Below five seconds the endpoint starts refusing; past a minute the table is stale enough that a slower dial wouldn't be asked for. The default is deliberately not the fastest the dial allows - see [Data sources](#data-sources).
- **Location** - the place search, which used to be a button filling half the main header. It is a setting rather than a permanent fixture of the table: it gets changed once when the device moves and then not again. Both finishing and cancelling return here rather than to the table, so a new location lands you back on the button that shows it took.
- **WiFi** - scans for networks and connects to one, so the device can move between networks without a reflash. Credentials are saved to NVS and win over the ones compiled in from `secrets.h`, which stay as the fallback for a device that's never had WiFi set on-screen. They are saved only once they have connected: saved up front, one mistyped password - or a tap on the neighbour's network - replaced those of the network that was working. A passphrase too short for WPA (or WEP) is refused before anything is tried. A device with no credentials at all - a fresh flash of a released image - opens this screen on boot rather than spending the connect timeout proving it has nothing to connect with, and Back from there lands on the table.

  A network that goes away is retried from the poll task, since being thrown into setup over a router reboot would be worse than the status line saying what is happening - but not indefinitely. Three failed attempts in a row, the boot connect included, is about a minute, and past that the network is taken to be gone rather than blipping (a phone's hotspot switched off, the device carried somewhere else): this screen opens, saying which network couldn't be reached, so another can be picked, and once one connects it goes straight back to the table. Only from the table, the radar or the detail screen - not from a replay or a half-typed watchlist, which don't need the network.
- **Alerts & recording** - which of the four alert kinds are on, whether an alert starts a recording, and the watchlist. See [Alerts](#alerts) and [Recording and replay](#recording-and-replay).

All of it persists across reboots, along with the mute state and the chosen location. Changing the filter, the range or the source refetches immediately rather than waiting out the rest of the interval; changing the interval itself doesn't - the new value simply applies to the wait already running, including shortening one in progress.

## Polling

These endpoints return around forty fields per aircraft and this app reads fifteen. The reply is read by a scanner made for it (`FeedScanner` in `src/adsb_client.cpp`) rather than by ArduinoJson: one pass over the bytes, each aircraft's fifteen fields copied straight into a plain struct of fixed buffers as they go past, the other twenty-five skipped without being worked out, nothing allocated - numbers rounded once to the nearest float, in the FPU's single precision where their digits fit a float exactly and in double where a position's eight or nine don't. ArduinoJson, with a filter to skip the rest, took time in the square of the reply: version 7 keeps one copy of each string, and finds whether it has one already by walking every string it holds - hexes, callsigns and registrations, nearly all different - so a 60nm poll of 36 aircraft took 15.7ms, Glasgow at 250nm (340) 214ms and central England (822) 1.3s, on the core the 3D view draws with. A document an aircraft fixed the square but still cost half a millisecond each, making and filling it. The scanner takes 3.5ms, 39ms and 99ms, the same aircraft field for field as ArduinoJson in double precision, checked on four saved replies (`##=p`, see bench2d.h). Where the response declares a `Content-Length` it is read straight off the socket; where it doesn't, it goes through `getString()` first, because `HTTPClient` de-chunks on the `getString()`/`writeToStream()` paths but *not* on the raw stream - a chunked reply read directly still has the chunk headers in it.

The HTTPS client is held for the life of the firmware rather than built per fetch, with `setReuse(true)`, so the socket stays open between polls and each fetch skips DNS, TCP and the TLS handshake. `HTTPClient` stores the client by reference and its `clear()` touches neither the socket nor the reuse flag, so this needs nothing more than keeping both objects alive. Measured with `-DNET_PROFILE`:

| | before | after |
| --- | --- | --- |
| fetch, start to parsed | ~340ms | ~90ms |

The build uses `-O2` rather than the Arduino default of `-Os`, which on a synthetic 66KB, 150-aircraft response cut the filtered parse from 79ms to 45ms. The same comparison left drawing unchanged - a full radar repaint draws in ~22ms and the table in ~44ms at either level, because writing into the PSRAM canvas is bound by the memory rather than the instructions - so the gain is the poll task's, for about 90KB of flash. The precompiled framework (WiFi, TLS, drivers) is untouched by either.

The first fetch after a boot still pays the full handshake, and a connection the far end has closed in the meantime shows up as a transport error on the next request rather than at the time it was dropped - so a *connection-level* failure retries once on a fresh socket. Only a connection-level one: a read timeout means the server has the request and is simply slow, and sending it again would put two of the same request on an endpoint that is already throttling. The read timeout is 12s rather than the 5s default for the same reason - a served request takes about 45ms, but a throttled one can take several seconds and is still worth waiting for. The standing cost is one mbedTLS context resident (about 380 bytes of static RAM here) instead of one built and torn down every ten seconds.

Providers answer `429 Too Many Requests` once they have had enough, and a poll that collects one is followed by a minute in which no request goes out to *that* provider at all, rather than by more of the same at the usual cadence. The backoff is per provider, so one throttling the device doesn't sideline the other. If 429s are a standing feature rather than an occasional one, the refresh interval in Settings is the dial to turn - a short one is not guaranteed to be within what the endpoint will serve, and a long session of reflashing (each boot polls immediately) is enough to trip it.

The kept-alive socket is closed when a poll is aimed at a different host, since reusing it would send the request down a connection to the wrong server.

**What is left out.** Not everything a feed lists is a flight, and the poll leaves out, whatever the callsign or type, the reports that can't be one: a ground station (type `TWR`, a fixed transmitter at an airport with a transponder address of its own); a height below anything on the deepest high, 1,500ft under the sea; and a height in the air with a groundspeed under a knot - nought, or readsb's 0.7 for a velocity of nothing - which nothing with wings flies at: a transponder left on, parked, that doesn't say it is on the ground, or one reporting nonsense, as a Typhoon was seen to with a height and nought knots. What really can stand still in the air is kept - a helicopter, by its category or its type, a balloon or airship, a parachutist, a hang-glider or paraglider, a drone - and so is a height with no speed at all, most often a position worked out from when its signals reached the receivers (MLAT), its speed to come. Tried on 2,061 aircraft from five areas and the military feed, 1,646 of them with a height in the air, the rule left out three - a PC-12 at 1,900ft and an A321 at -50ft, both at 0.7kt and plainly parked, and a transponder claiming 80,000ft - and kept three helicopters hovering at 0.7kt; 91 had no speed at all, nearly all light aircraft and military jets placed by multilateration. A recording made before the rule replays without them too. The first time each is left out, the log says so - `[adsb] <hex> <callsign> <type> at <height>ft and <speed>kt: standing still in the air, left out`. And the app makes none of its own: a contact the feed loses in the air with no speed to carry it on by is let go, as one flown out of range is, rather than held where it was - which stood it still in the air at nought knots - and a speed the feed never gave is `?` on an estimate's details and in the 3D view's strip, never 0.

The status line under the table says how old the data is, and turns amber when the last poll didn't land, so a quiet sky can be told apart from a dead network. A link that drops is reconnected from the poll task with a 5s-to-2min backoff, standing down while the WiFi screen is up, since that screen drives the radio itself; three failures in a row open that screen (see [Settings](#settings)).

## Aircraft types

The `desc` field is always null on the endpoints this uses, so the detail screen's full aircraft name is filled in locally from `src/aircraft_db.cpp`. There are two tables: civil types, and around 85 military ones covering transports, tankers, surveillance, combat, trainers, helicopters and drones.

Which is consulted first depends on the aircraft's own military flag, because a good number of ICAO designators cover both - `EC45` is an air ambulance or a US Army UH-72 Lakota, `BE20` a King Air or a C-12 Huron, `B762` a 767-200 or a KC-46 Pegasus. The other table is still searched as a fallback, so a type listed in only one resolves either way.

Every designator in both tables is checked against the ICAO doc 8643 list rather than written from memory, which is how four bad entries came to light - each one a row that could never have matched an aircraft:

| was | problem | now |
| --- | --- | --- |
| `RC135` | designators are four characters at most | `R135` |
| `TYPH` | not a designator | `EUFI` |
| `E175` | not a designator; the E175 is split by wing | `E75L` + `E75S` |
| `PA28` | not a designator | `P28A` (already present) |

## Radar

The radar button in the header opens a plan-position plot centred on the configured location, in phosphor green: range rings on round numbers, bearing marks every 30 degrees, and every contact that reported a position as a blip with a vector showing a minute of flight at its current groundspeed. A tap on a blip opens that aircraft's detail screen.

A single hue is deliberate - on a plot like this brightness is what carries meaning, which leaves it free to mark a new arrival as the brightest thing on screen.

Which is also why vertical movement is a shape rather than a colour or a shade: both of those were already spoken for, and neither was free to take on a second meaning without muddling the first. A contact that is climbing carries a chevron above the blip and one that is descending carries it below, pointing the way the aircraft is going; level and ground traffic carry nothing at all, so the plot stays quiet when nothing is doing anything vertically. The footer names the two marks rather than leaving them to be worked out, stacked above the contact count in the bottom right: the plot is still 165px wide at the footer's height, so a legend appended to the range line on the left ran straight into it. Each of the three readouts sits in its own boxed cell the way a scope's data blocks do, drawn in the same dim green as the range rings so the boxes read as furniture and the text inside them as the reading.

That is roughly what a real secondary-radar display does, for the same reason - the scopes those plots were drawn on had one phosphor and no colour to spend, so trend information went into the symbol.

A data refresh redraws only what can change: the plot square, and the footer readouts beside it. The header and the margins either side of the plot stay as they were drawn on arrival, which halves the area pushed to the panel, and the square is cleared by the PPA rather than the CPU - 15ms of `fillRect` into PSRAM, where the hardware fills the whole screen in 5. Measured with 60 contacts, a refresh went from 64ms to 41ms; arriving at the screen, or toggling its centre, is still the full 64ms repaint. Contacts are clipped to the square so that nothing is drawn outside what a refresh erases - at short range a fast aircraft's vector can otherwise run well past the outer ring.

Callsigns are placed nearest-first, below and to the right of the blip, or failing that to its left, or above either side - clear of the labels already placed and of the map's own: the airports' and navaids' labels and symbols, the ring distances and compass points, which a callsign used to be written over (`GLA` under one leaving Glasgow). With nowhere clear, it isn't labelled, so in a cluster the closest aircraft keeps its label and the rest stay as bare blips; a followed or alerted one is labelled regardless. In the airport zoom, one stopped on the ground - parked at a stand, as dozens are at a busy airport - is its ring alone, unlabelled unless it is followed or alerted: their callsigns and `GND`s were a heap over Heathrow's runways, and what is moving is what there is to read. The footer says how many were plotted and how many of those are labelled, so a thinned display doesn't read as a missing one.

The code at the centre is the nearest airport, from a generated table of the 3244 large and medium airports with scheduled service in the public-domain [OurAirports](https://ourairports.com/data/) dataset (~39KB of flash). A full scan takes 6.7ms, so the result is cached until the location changes rather than recomputed per frame. Nothing within 120nm leaves the centre as a bare cross.

An alerted aircraft is drawn amber, or red for an emergency, and as its alert goes off its callsign flashes red three times - drawn even where it would otherwise give way to another label, since it is the one being pointed at. REC and Replays sit in the header; see [Recording and replay](#recording-and-replay).

The buttons stand in a column down the right-hand edge, each doing one thing on a tap - there is no long press on the radar. Under **Back**, **HOME**, **AIRPORT** and **ALL** choose the view, only the one in use lit: **AIRPORT**, the default, puts the airport nearest home at the centre, marked with its airfield symbol and code in white; **HOME** centres on the configured location itself and marks it with a bare `+`, which is home's alone. The choice persists. Airport mode with nothing in range falls back to home. The aircraft are still fetched around home, so with the plot centred on an airport some way off, the edge of the plot furthest from home can sit beyond the fetch radius and show empty. Below them come **FOLLOW**, then **REC** and **Replays**, and last **ZOOM IN** and **ZOOM OUT**, which step the range shown through 5, 10, 15, 20, 30, 40nm and on (`RADAR_RANGE_STEPS_NM`) - at the default 25nm, the same steps as following closes in through on a landing. Inside the poll radius they change only what is shown: the poll, the table and the alerts go on covering the whole radius. **ZOOM OUT** past it widens the radius itself, as the settings slider would and as far as it goes - 60nm, 250nm with a filter on - saved, and shown on the settings screen; and **ZOOM IN** from 5nm opens the airport zoom of the airport at the centre - centred on home, the nearest within 5nm - with its ZOOM OUT coming back to 5nm. Past the ceiling, **ZOOM OUT** goes on over the map alone, through 200, 300, 500, 750, 1000, 1500 and 2000nm (`MAP_RANGE_STEPS_NM`), with the title saying `map only`: the outlines and their names, and no traffic, navaids or airports - at 500nm there would be hundreds, though ALL puts them all on - with the range rings, if they are on, every 100, 250, 500 or 1000nm. Free look drags it as it does any plot, a swipe now crossing a country or a sea, and **ZOOM IN** comes back down through those ranges to the radius and its traffic, fetched around wherever it was dragged to. The poll, the table and the alerts carry on around home throughout. A map range isn't kept across a reboot, and **FOLLOW**, or an alert's auto-follow, brings the radar back in to the traffic. Either is greyed out once there is nowhere further to go. While following they step through the range around the aircraft instead - see **Follow me** below. The range chosen persists.

The radar and the airport zoom act on a touch as it lands rather than as it lifts. Elsewhere a tap is M5Unified's click, which only counts if the finger lifts within half a second and less than 8px from where it landed - on the radar enough taps strayed past one limit or the other that its buttons felt laggy or missed taps outright, and a tap held a moment too long on the old centre toggle toggled the airports instead. Nothing on either screen holds, and the one thing that drags - the plot itself, by its empty sky, see **Free look** below - is a touch that found nothing to act on, so nothing is lost; the rest of any other touch is ignored, so a tap that opens another screen doesn't go on to press whatever is under it there. Each button also takes a tap from the margin to its left and halfway into the gaps around it, and lights before the plot is redrawn.

**ALL** is the airport view with every other airport within the plot's range marked as well; HOME or AIRPORT takes them off. Each is a chart's airfield symbol - a ring with four ticks, so it can't be mistaken for a blip - with its code under it, in the dim green of the compass points and drawn before any contact, so the airports read as the map and the traffic stays on top. Codes are placed nearest-first, every symbol before any code: each under its symbol, or failing that over it or to either side - tried first where it was on the last plot, so one going past a compass point as the map moves under a following doesn't flick from side to side - clear of the other labels and of the compass points, ring distances and other symbols, which a code used to be written over. One with nowhere clear is left off with its symbol kept, so a cluster of airfields still shows as one, except the airport a departure took off from; callsigns don't give way to them. Over the busiest parts of the table that comes to about 25 airports at 150nm, and 5 to 10 at 60nm. The list comes from the same table, cached until the centre or the range changes, and the choice persists and carries over to replays.

**Navaids** - the radio beacons on an aviation chart - are marked in every view, following and replays included, unless switched off in settings: each VOR, VOR-DME, VORTAC, TACAN, DME and NDB-DME in range, as a chart draws it but small - a hexagon with a dot for a VOR, boxed for a VOR-DME; three tabs for a TACAN, round a hexagon for a VORTAC; a box with a dot for a DME, round a ring of dots for an NDB-DME - with its ident and what a pilot would dial beside it: `GOW 115.40`, an NDB-DME's NDB in kHz (`CBN 374`), a TACAN's channel (`AAL 114X`). They are drawn after the airports, in the ring labels' dimmer green, as the part of the map least often looked for. A label goes to the right of its symbol, or failing that the left, above or below - inside the outer ring and clear of every other label, every airfield and navaid symbol, the centre's cross or the followed aircraft's ring, and the ring distances and compass points - and one with no room anywhere keeps its symbol only. Each is tried first where it was on the last frame and let stay there with a little less room, so as the map moves under a followed aircraft a label that only just fits doesn't come and go a pixel at a time. One whose symbol would touch an airfield's is left off altogether: it is that airport's own, at a range where the two can't be told apart - Glasgow's GOW at 20 and 10nm - and a closer range, or the airport's zoom, has room for it. A tap on one - its label or its symbol, or picked from the list where it is among airports or traffic, as Glasgow's GOW is - puts up its card: its name, type, frequency, DME or TACAN channel, and the airport it serves; the next tap anywhere closes it. They come from OurAirports' navaids, generated by `tools/gen_navaids.py`: 4397 of them, by latitude so the radar's lookup goes straight to its band, about 200KB of flash. Plain NDBs, twice as many again and clutter round every airfield, are left out, as are the few the dataset marks closed. The airport zoom has them too, over its runways, their labels kept clear of the runways, their in-use arrows and numbers: GOW 115.40 beside Glasgow's 05/23.

**The map** is under all of it, drawn first: coastlines and lakes as a solid line, countries' borders dashed, and the state and province lines of the United States, Canada, Mexico, Brazil and Australia - where a plot can be a long way from any coast or border - dotted, as an atlas has them. All in one grey-green no brighter than the rings, since it is there to say where the traffic is rather than to be looked at; in every radar view, following and replays included, unless switched off in settings. It is [Natural Earth](https://www.naturalearthdata.com/)'s 1:10m set, public domain, and all of it - the whole world, so it is there wherever the device or a followed aircraft goes: 786,030 points in 2MB of flash, none of the PSRAM - the lakes of Natural Earth's four lake layers joined into one first, where they overlap or meet across open water, so a lake's shore only ever runs between water and land. `tools/gen_coast.py` does everything that can be done ahead: the lines cut into cells a degree square, only the 11,698 with anything in them listed, in order for a search to go straight to; and each line stored as a start and then steps of a signed byte each way on a 54m grid, two bytes a point. A plot looks up the cells under it, places each point with the radar's own flat-earth projection - so a coast is where the traffic over it is plotted - and writes the lines straight into the canvas's pixels, cut off at the outer ring. Flash holds one level of detail: Natural Earth's points are a mile or so apart, already further than a pixel at 150nm, so a second level with every bend under 250m taken out still had two thirds of the points, and would have cost two thirds the flash again to spare the widest ranges a third of their strokes. Out on the map's own ranges, though, a pixel is kilometres across - ten of them at 2000nm - and a first draw there read 200,000 points to keep 36,000; so two thinned copies are built at start-up, on core 0 in the background, from the table in flash into PSRAM, in the same layout and read by the same code: each line through no more of its points than keep it within 32 or 64 steps of the grid (about 2 and 4km) of where it ran - the Douglas-Peucker way - and drawn only where that comes to half a pixel or less, 750nm and out and 1500nm and out round Glasgow. The other way, close in, those points would make a coast of straight edges a hundred pixels long, so a coast or a lake is drawn as a curve through its points - a centripetal Catmull-Rom spline, the kind that can't loop or overshoot however unevenly they are spaced - while borders and state lines stay the straight lines so many of them are: Colorado keeps its corners. That makes a coast smooth, not more accurate. It is where it should be to a few hundred metres, which is right for a radar and wrong against a runway drawn to scale - Hong Kong's and Kansai's islands are a guess at best - so the airport zoom is left without it. The pixels a plot's map comes to are kept, in PSRAM, for the next draw of the same plot, which is every draw while nothing is being followed: at 150nm round Glasgow, with the whole west coast of Scotland on it - 14,000 pixels - working the map out took 12ms and putting it back 4ms; at 20nm, 2ms and 1ms. Working it out - a first draw, at a new range or as a followed aircraft moves the plot - was taken from 149ms to 32ms at 2000nm, 63ms to 19ms at 1000nm and 15ms to 8ms at 250nm in 1.4.1, the same pixels apart from the thinned levels', by three things. A point is passed over or kept in the grid's own whole numbers, and only those kept are turned into the canvas's floats, where every one had been, and pushed onto a list; with the line's state copied into locals for the loop, which the compiler had been keeping on the stack and loading and storing for every point - it was some 200 cycles a point, and is now held up on memory rather than instructions: the trick a hand-written loop would use, one compare for each of the two distance tests, changed nothing. The cells are found a row at a time - one search for each row's first, and then only the cells that have anything in them - where every square degree in the plot's reach had been searched for, open sea and all: 30ms of the 149. And the cells are shared out between the two cores, each taking the next not yet taken, which share their data cache and so the canvas: 1.6 times as fast, the same pixels. What is left of that is the canvas rather than the code: it is in PSRAM behind a cache far smaller than it, so each pixel put on it is a line of the cache fetched first, a quarter of a microsecond a pixel, where reading the kept list is under a millisecond of the four. Three other ways were measured on the device and were no better: keeping the strokes instead, to step along again, took 6ms; the pixels sorted into the order the canvas is in memory, 4ms still and 3ms more to sort; and a whole plot kept ready-made for the PPA to copy takes it 23ms, longer than drawing everything on the plot afresh. `tools/coast_preview` draws any plot's map on the PC with the same code, to see a change without flashing it.

**The names** go on the map with it: the countries; their regions - states, provinces, counties, council areas; the seas, bays and straits; and the lakes - in the map's own grey-green a step brighter than its lines, a sea's or a lake's a little bluer, in spaced capitals, over the outlines and under everything else - drawn just before the traffic, clear of its labels as the last frame placed them as well as of the map's, and only onto the plot's background and the map's own lines, a pixel at a time in the font's own letters, so a contact, its vector or a trail crossing a name stays whole. They are placed afresh whenever the plot is drawn whole, and at least once a minute, so between times they stay put as the traffic moves rather than hopping out of a label's way at every frame. Each sits where its outline has the most room for it, which `tools/gen_names.py` works out ahead from Natural Earth's polygons: the middle of the biggest box the shape of the name that fits inside, rather than the centroid, which for a bay or a horseshoe is off it - and for a name of two words or more, on two lines where they make more of the room. With the spot goes how big that box is, so the plot sizes the name to its room at any range: zooming out, a council area's name shrinks until it is too small to read and goes, and its country's comes into view; zooming in, the other way, up to a cap that keeps a country a quiet word rather than a banner. Between the font's sizes the letters spread apart, so a name grows with the range rather than in steps. A name is shown only while its spot is on the plot and all of it fits inside the outer ring, clear of the airports, navaids and their labels, the traffic's labels, the ring distances and compass points, and the names before it - countries first, then seas, regions and lakes. And the United States' counties - Natural Earth's only second-order divisions - shown from closer in than the rest, needing more of their room before they are. A big area - a state, a province, a sea, a lake - has spots of its own across it besides its middle, every 50, 100 or 25nm, each with the room it has there worked out the same way, so that its name is found close in, where its middle is off the plot: Illinois and Lake Michigan round Chicago at 60nm, which had none. Each area is shown once - at its middle if that is on the plot, or else at the nearest of its others to the plot's middle - and the oceans have their middle alone, spots across them being ten thousand of open water. About 25,700 spots for 10,400 areas, the whole world, in some 600KB of flash, sorted by latitude for a plot to search only its own band. Which of them could go on a plot - the band looked through, one spot an area, in the order they are tried - is a matter of where the plot is and how far it reaches, so it is kept from one draw to the next and worked out again only when that changes: at 2000nm it is some 18,000 spots and 12ms, every frame until 1.4.1, and trying the few that come of it against the traffic's labels is next to nothing. It is in floats, which the P4 does in hardware, where doubles are worked out in software: 0.3ms rather than 3 at 250nm. Natural Earth's slips are put right there: North Ayrshire, Perth and Kinross.

**Cargo flights** - FedEx, UPS, DHL and two dozen more cargo operators, by their callsigns' airline codes in `src/aircraft_db.cpp` - have their callsign in sky blue on the table and the radar, where nothing else colours it, the operator's name in its colours with a `CARGO` tag on their details, a **Cargo** chip of their own on the filter, and their name said by the voices: "FedEx one two three". A cargo flight under a passenger airline's callsign, as Qatar's and Emirates' are, can't be told apart, and isn't marked.

**The filter**, the funnel in the table's header and beside the speaker in the radar's title, cuts down what the table and the radar show: a band of height, GND to 45,000ft in thousands, and of speed, 0 to 600kt in tens, each a slider with two knobs, its top meaning no limit; civil, cargo or military aircraft, any of them; and airlines and types, typed as the watchlist is - `EZY RYR`, matched against how a callsign begins, and `A32 B738`, against how a type designator does - and beside the types, **hide types**, those left out whatever else: `TWR`, the fixed ground stations some feeds list among the aircraft. While one is on both funnels are lit, the strip under the rows says `12 of 40 pass the filter`, and the radar's title says `filtered`. The aircraft followed, the airport zoom and alerts are never filtered - an emergency is never hidden - and an aircraft whose height or speed isn't known is left out by a band that has been set. A recording keeps every aircraft, with the filter in force written into it as it changes (a `Q` line), so a replay shows the radar through it as it was seen live - `Replay - CRG`, the funnel lit after it - and an older recording, which doesn't say, everything. It is kept through a reboot; **Clear all** on its screen puts everything back. With a filter on there is room to look further: the range ceiling, on the settings slider and the radar's ZOOM OUT, rises to 250nm - as far as the feeds' area queries go - from 60nm, coming back down as the filter is cleared; the radar steps out through 150 and 200nm, and past 150nm draws the navaids without their labels, which would bury the traffic - a tap on one still opens its card. A 250nm poll round Glasgow is about 100 aircraft and 60KB, fetched and parsed in under 200ms, and round London about 350 and 200KB; and where the poll keeps the nearest sixty aircraft, it keeps as many again beyond them that pass the filter, so the table and the radar fill out to the edge of the radius rather than showing what passes of the nearest sixty. The nearest sixty are kept whatever they are, for the alerts and recordings.

**The sound's switch** is at the end of the radar's title and the zoom's, as it is in the table's header - the one switch, shown in all three - since the voice speaks on these screens, the zoom's clearances above all. Under it in the margin, above the range, a **clock** - `14:32Z`, as aviation keeps time, or a zone's local time, `14:32 BST` - redrawn as the minute turns over, for a tracker left on a desk or a wall; its zone is picked, or it is switched off, on the display page.

**The range rings** inside the outer one are a setting, and off unless switched on: with the map under the plot they are no longer all that says where anything is. Without them the plot keeps its outer ring, with the range on it, the compass points and the bearing marks; the map is drawn a little brighter; and a frame is quicker by the rings - 2ms at 150nm, where there are two of them, and 1ms at 20nm.

**Free look**: put a finger on the plot where there is nothing to tap - empty sky - and drag, and a line stretches out from the middle of the plot the way the finger goes and as far, with a ring on its end and beside that how far it is and on what bearing: `13.6 nm  BRG 054`. Let go, and where the ring was is the new centre, at the range the plot had: the title says `free look`, neither HOME nor AIRPORT is lit, and either puts the radar back. ALL is lit there if it was on, and tapped on a free look it stays where it is: it marks every airport around it - as a free look does anyway, and out on the map's own ranges, which otherwise leave them off. The swipe is relative - it need not start at the middle - and the next one goes on from where the last left the plot, so the radar goes anywhere, a swipe at a time. While the line is out the plot stays as it was, to read the line against - and is kept as it was drawn, in 1MB of PSRAM, so each move of the finger puts the plot back only where the line and its box were and draws them where they are, pushing just those: 6ms a move on the radar and under 5ms in the zoom, where drawing and pushing the whole plot again was 59ms, 17 frames a second behind the finger - with every airport in range marked whichever view it is, as something to aim at. A swipe across the whole screen is twice the plot's range, so the line can run off the edge of it: then the plot is drawn again at the first range that takes the line, with its coast, lakes, borders and airports and none of its traffic - a drag out of a 25nm plot to Edinburgh, 38nm off, shows at 60nm - and the traffic comes back when it is let go. Dragged off its centre, the radar is centred on nowhere in particular: a small dim cross marks the middle, home keeps its own bright one where home is, and every airport in range is marked, to tap for its zoom as ever. The traffic around the new centre is fetched for it, as it is around a followed aircraft: the extra poll that serves the zoom and following is aimed there, at the range shown, of the same traffic - civil or military - as the table, one more request per poll while the radar is up and dragged off. The main poll, the table and the alerts go on being of home; so does a recording, which a free look is left out of. Until the first answer lands, a few seconds on, the main poll's list stands in. An airport's zoom opened from there, and ZOOM IN from the closest range, are of the airport there; its ZOOM OUT comes back to the radar where it was left. Following takes the centre for the aircraft, and HOME or AIRPORT takes it back.

The airport zoom drags the same way - to look along an approach, or at the far apron of a big field at taxiway level - but stays its airport's: the middle goes no further from the middle of its runways than its framing reaches, which is as far as its traffic is fetched, and **CENTRE**, under INFO, lit once it has been dragged, puts it back. Neither drags while following, which has a centre of its own.

**Tap an airport** - its code or its symbol, the centre's included - to zoom in on it. Where a tap reaches more than one thing - an airport under its own ground traffic, or a cluster of contacts, on the radar or in the zoom - a list of them comes up beside it, airports first and then the aircraft by callsign, type and altitude, to pick from; anywhere else, or Cancel, closes it. The zoom draws each of its runways to scale from where the dataset puts its two ends and how wide it is, with the number painted on each end just beyond it and a dashed extended centreline running on to the edge of the plot. It is centred on the middle of the runways and framed to fit them with room around for traffic on final: 2nm across for a one-runway field like Glasgow, 2.5nm for Heathrow, 4nm for O'Hare. **ZOOM IN** and **ZOOM OUT**, where the radar has them, step it through 0.5, 1, 1.5, 2, 3nm and on: in to the taxiways, where a crowded apron's contacts come apart - at 0.5nm a mile is nearly 700 pixels - and out to the framing, past which **ZOOM OUT** goes back to the radar, as **ZOOM IN** at 5nm on the radar comes here. Following, zoomed in past the framing, the zoom is centred on the aircraft instead of the runways' middle and redrawn every second, so it can be watched touching down, rolling out and taxiing to its stand at 0.5nm with the runways passing under it; when it hands the aircraft back to the radar is still decided by the framing, whatever the range shown. The traffic is the radar's, drawn the same way, except that aircraft on the ground are rings rather than dots, each callsign has its altitude under it, and vectors reach 20 seconds ahead instead of a minute. A runway end is shown **in use** - its number brightened, its approach line too, an arrowhead on the runway just inside that end pointing the way it is being used, and listed over the range at the bottom left; for 30 minutes after (`RUNWAY_IN_USE_MEMORY_MS`) it keeps a dimmer arrow and is listed as **last in use**, so a lull still shows which way the airport is working, in replays as live - while something in the air is lined up on it: within 2500ft of the field, within half a mile of its centreline and pointing along it - arriving, or climbing out. Traffic on the ground doesn't count: a vehicle racing down a runway and back can light both its ends, as a runway inspection car on Heathrow's southern runway most likely did. The radar is redrawn between its polls too, with each contact moved on along its track at its groundspeed, up to two intervals past the last poll - as often as the fastest contact on the plot moves a pixel, from eight times a second close in to every 5 seconds far out, where nothing moves a pixel sooner - so the sky glides rather than steps. Only the contacts actually drawn count: one left off by the filter or beyond the outer ring doesn't set the pace. Tapping a contact opens its details as usual. **Back** goes to the table, as the radar's does, and the radar opened from there comes back to the zoom as it was left, at the range it was showing - after a reboot too, the airport and range being saved with the other settings - unless an aircraft is being followed, when it is the radar centred on it that comes back; **ZOOM OUT** from the framing is the way back to the radar itself.

While the zoom is up it fetches the traffic around its airport every 10 seconds (`ZOOM_POLL_INTERVAL_S`) - it was 5, until adsb.lol began answering `429` over a landing - and is redrawn between fetches with each contact moved on along its track at its groundspeed, and a followed one by the estimate below, as often as the fastest of them moves a pixel - at its framing an airliner on final does eight times a second - so the traffic glides in rather than jumping every ten seconds; a few miles past the plot so arrivals are counted before they reach it. It is a separate fetch into a separate list, so the main poll, the table, alerts and recordings carry on unchanged, and no two requests go closer together than `POLL_INTERVAL_MIN_S`. It stays up, fetching around its framing whatever the range shown, until **ZOOM OUT** or another screen takes over - left on an airport, it keeps watching it. The runways come from a table generated by `tools/gen_runways.py` from the same OurAirports data: 4339 runways at 2874 of the 3244 airports, about 155KB of flash. The 237 the dataset marks closed - Glasgow's old 09/27 among them - are drawn the way a chart draws one, outlined and crossed out under the open runways, with no numbers or approach line, and are never taken to be in use. The rest have no runway ends in the dataset, and their zoom says so and shows only the traffic.

**INFO**, in the zoom - where the radar has HOME, the first of the buttons the zoom has no use for - puts up the airport's card over the plot: its IATA and ICAO codes, its name, its elevation, and the radio frequencies someone with a scanner would tune to hear it, a row for each use it has any for - `TOWER`, `GROUND`, `DELIVERY`, `APPROACH`, `DEPARTURE`, `RADAR`, `CONTROL`, `ATIS`, and `INFO` for the information or traffic frequency of a field without a tower - with up to four frequencies to a row, in MHz: `TOWER 118.500 118.700 124.475`. Beside them is a radar on a lattice mast, its dish tilted up and three arcs of what it sends going out, drawn in lines as the navaid symbols are. The next tap anywhere takes the card off; until then the plot's refreshes are drawn under it. The frequencies come from OurAirports' `airport-frequencies.csv`, by `tools/gen_airport_info.py`: 8282 of them at 2685 of the table's 3244 airports, with the names, about 170KB of flash. A frequency there belongs to an airport and has no place of its own - nothing says where a tower's aerial or a radar's head stands - which is why they are on the airport's card rather than marked on the radar as the navaids are. The dataset's types are a few dozen spellings typed in by hand over the years, sorted here into the nine; where the type alone doesn't say, the description does - an approach frequency that describes itself as `SAN JUAN CNTR` is the centre. Left out are anything outside the VHF airband and the military UHF one - there is HF, and typing slips, in there - flight service and company frequencies, and the automatic weather stations. It is as complete and as current as its volunteers have made it: most airports have their tower and approach, far fewer a radar or a control centre, and one in six has nothing listed, which its card says.

**Follow me**: tap **FOLLOW** - it says TAP PLANE - then a contact, and the radar centres on that aircraft at 20nm (`FOLLOW_RANGE_NM`), ringed and always labelled, with its callsign in the title and the airports around it marked whichever view it was picked from, wherever it goes: it is fetched around the aircraft by the zoom's extra poll, so it carries on past the edge of the radius. On the radar that fetch goes at the main poll interval - one extra request per poll, never closer than `POLL_INTERVAL_MIN_S` to another - and only the zoom fetches every 10 seconds. Coming down to an airport - below 12,000ft, not climbing, with an airport within 20nm off its nose, or within 4nm whichever way it points - the range closes in on it in steps, 15, 10 and 5nm (rings every mile at 5), keeping the airport on the plot without the miles beyond it; the fetch shrinks with it. A level-off on the way down, or a poll that misses its airport, doesn't end that: two polls running without one, or a climb, do. **ZOOM IN** and **ZOOM OUT** work while following too, through the radar's ranges from 5nm out to as far as the poll may reach - 60nm, 250nm with a filter on - the fetch around the aircraft going with them, and out at once rather than at the next poll. A range picked is held until the next landing or take-off, when the landing's framing takes over, or the climb's 20nm. With **auto zoom**, a switch among the radar's on the settings screen, the climb and the cruise size the range to the sky around the aircraft instead: out a step while fewer than eight others are on the plot, and in a step while more than twenty are (`AUTO_ZOOM_FEW`, `AUTO_ZOOM_MANY`), no closer than 10nm - airborne ones, counted through the filter, so a cargo flight followed with the filter down to cargo opens the plot right out. A step is taken only where the range after it, going by how many there are to the square mile now, wouldn't swing it straight back; out at once, the wider sky fetched straight away, and in only when two polls running agree, so a crowd passing through doesn't pump it in and out. The range readout says `40 nm auto range` while auto zoom has it. Coming down to land and climbing away are framed as before, whatever it was at - with auto zoom in finer steps, 15, 12, 10, 8, 6 and 5nm (`FOLLOW_FINE_STEPS_NM`) - and once it is handed to its airport's zoom, auto zoom follows it in there too: in a step at a time through the zoom's own ranges as it nears the runways, so their middle stays on the plot around it, then from touchdown, through the rollout and the taxi, at 0.5nm; a take-off the other way about, out a step at a time as it climbs away until the radar has it again. A step in waits until it is well inside the next range down, and a step out until it no longer fits, so a report jittering at an edge doesn't pump it; the zoom's own ZOOM IN or OUT holds a range until the next touchdown or lift-off. Each zoom range it picks is recorded as the radar's are, a `Z` line, for a replay to match. The recordings list says `auto zoom` against a follow recorded with it on, and otherwise the range it began at. A recording keeps each change of range with when it was made - an `R` line, written ahead of the next poll - so a replay of a follow changes range when the live radar did, between polls as often as not; an older recording is framed the way following used to, from each poll. Low near an airport - any within 10nm, not only the nearest, since on final to one it can pass closer to another: within 2500ft of the field, not climbing, and inside that airport's zoom, or due to be by the next fetch at the speed it is doing - it is handed to the airport zoom, to watch it touch down or roll for take-off with the runways in use lit, and back to the radar as it flies off the zoom's plot - in the air, further out than at the last poll, and off the plot by the next at its speed - so a departure is on the radar as it climbs past the edge rather than a mile after. While following, the margin left of the plot shows its **height telemetry**: altitude, vertical speed and groundspeed as last reported, and a chart of its height over the last 10 minutes, a point per poll, with each touchdown (**TD**) and take-off (**TO**) marked where the change was first seen. On the ground it is drawn at the elevation of the field it is on, so a landing meets the ground where the ground is. In an airport's zoom the field's elevation is drawn across the chart and the height above it (**AGL**) joins the readouts. **Take-offs and landings are simulated** rather than pieced together from the feed's reports, which come and go near the ground. A landing is simulated from when it is lined up on final, under 2,500ft over the field and not climbing: it is held to the runway's centreline, flies on to the touchdown point - its height brought down from its last report to the field's by then, which lines the barometric altitude up with the ground - and rolls out, braking at 2.2kt a second to 20kt and then gently to a stop, no further than the far end. It waits there until a report puts it off the runway, then turns off and taxis to where that report has it, since without the taxiways it can't be said where it would turn off before then; a go-around hands it back to the feed. Each report while it is under way corrects the simulation rather than replacing it, eased in over a few seconds, so the plot never jumps. When the feed loses it - most often at the touchdown, as it drops below the receivers' horizon until it is taxiing near one - it is drawn dimmed and redrawn every second, with the telemetry saying how long it has been lost. Anything else carries straight on in the air; taxiing, it carries on along its track for up to 12 seconds between reports, and stopped it stays put. Distance along the runway rather than height decides the touchdown, since the feed's barometric altitude reads a few hundred feet out when the pressure is high or low. Checked against an arrival at Glasgow the feed lost for 53 seconds, the estimate had it within a few hundred feet of where it reappeared, at 92kt to its 83. Replays estimate it the same way. Every other contact is simulated the same way, and one the feed loses is kept for up to 90 seconds (`ESTIMATE_LOST_MS`), or three minutes taking off or landing (`RUNWAY_SIM_LOST_MS`) - if it was low, under 4,000ft (`ESTIMATE_MAX_FT`) or on the ground, where the receivers lose them; or at any height, if the poll it went missing from was answered by a different provider than the last that had it, as when adsb.lol answers `429` and the poll falls back to adsb.fi, which around Glasgow has a fraction of the sky. Each poll's provider is recorded for replays to tell the same. It is drawn on the radar, in the zoom and in replays alike, and is moved on between polls by it too, so one rolling out slows down the runway rather than carrying on at touchdown speed. Otherwise one that goes missing has most likely flown out of range, and is let go. An aircraft's **detail screen** has **FOLLOW** beside Back too, to follow it straight from there - from the table or the radar on the radar centred on it, from a zoom in that zoom - or **UNFOLLOW** for the one being followed; a replay's details have neither. **Auto-follow**, on the alerts screen, follows the aircraft an alert is for as the alert fires, unless one is followed already: from the table, the radar or a zoom the radar comes up centred on it, and anywhere else it is followed out of sight. With auto-record on too, it is recorded as any following is. Tapping another airport open while following leaves the following running - that zoom's poll doesn't reach the aircraft, so its absence from it isn't taken for losing it - and the zoom's ZOOM OUT goes back to it, the poll aimed where it is reckoned to be by then. **FOLLOW** is on the zoom too, in the same place and working the same way - tap it, then a contact - so one can be picked at the gate in the zoom; followed from there, the zoom stays on its airport until the aircraft has flown clear of it. **Departures** work the same way the other way round: follow one at the gate or taxiing and it is handed to its airport's zoom, with the telemetry, the frames between polls and the recording all as for an arrival; its take-off is simulated from when its thrust picks up on the runway - on its pavement and turned at least half way onto it, since one can be lost still turning on, and rolling faster than a taxi or 8kt faster than at its report before: accelerated down the centreline at 3.5kt a second, lifted off at 145kt - by the far end at the latest - and climbed out on the runway's heading at 2000fpm, until it is 1,500ft up, 3nm past the runway's end or turning off its line, when the feed has it again. Stopped on the runway itself - on its centreline and pointing along it, which a holding point some 90m off it isn't - and lost by the next poll, it is taken to have begun its roll from a standstill: it was lined up to go, and the feed losing it is as likely as not its going. A roll down the runway is taken for a departure unless the aircraft was in the air in the three minutes before, or was going faster a moment before. Once it has climbed out of the zoom it is back on the radar, and followed on past the radius for as long as you like - only auto-follow, with nobody there to stop it, ends once it is beyond the radius, along with its recording. Waiting at the holding point stops neither, since only a stop after being in the air counts as an arrival. Each update while following logs a `[follow]` line over serial - altitude, speed, status, the airport it is taken to be heading for and how far, the range, and any hand-off - so one that wasn't handed over can be worked out afterwards. The zoom's **ZOOM OUT** goes back to the radar centred on the aircraft and doesn't hand it to that airport again; its **Back** goes to the table, following carrying on out of sight. **FOLLOW** again (it is on the zoom too, while following), **HOME**, **AIRPORT** or **ALL** stops following, as does the aircraft vanishing from the feed for 90 seconds (three minutes taking off or landing); Back leaves it running out of sight.

With auto-record on, following starts a recording - taking over from one an alert started, which would only show it around home, but leaving one started with REC to run - marked *Follow* with the callsign in the recordings list. Following by hand, it runs until following is stopped or REC tapped - on past the aircraft parking, and past it being lost, when following ends but the recording carries on until REC. Auto-follow's stops by itself too, there being nobody to stop it: when the aircraft, having been seen in the air, is on the ground reporting no speed (or zero) - parked - or when following ends. Unlike the others it is made of the polls fetched around the aircraft rather than around home - at the main interval on the radar, every 10 seconds once handed to an airport's zoom - each marked with the view it was fetched for, so it follows the aircraft wherever it went. A replay of it shows it the way it was seen: the radar centred on the aircraft, gliding with it between polls, switching to the airport's zoom, runways and all, where it was handed over and back again as it left - and so does a video exported from it. The telemetry replays with it, on the right under the buttons, up to the moment shown. HOME and AIRPORT show in its replay only while the poll on show is of the sky around home, from before or after the following - there is nothing else to centre.

## The 3D view

**3D**, beside FOLLOW on the radar and in the airport zoom while an aircraft is followed, shows it in 3D: a 1008x560 picture with the camera buttons in a column beside it, and under it the callsign, type, height, speed, climb and the local time where the aircraft is. The aircraft is one of 25 shapes at their real sizes - from a Cessna to an A380, fighters, airlifters and helicopters, propellers and rotors turning - picked from its ICAO type and painted in its airline's colours where the callsign is one of 51 airlines. It is flown the way its track says: banked into its turns as steeply as a coordinated turn at its speed calls for, its nose along its climb and a few degrees above, raised in the flare and held up as the main wheels touch, then lowered onto the nose wheel; gear and flaps out on the approach; the spoilers springing up on their hinges as the main wheels touch, and coming down as the roll-out slows. The traffic around it is drawn too, each with a label - two lines, one or the callsign alone, by how busy the view is. The sky, the light and the shadows follow the real sun where the aircraft is, and after dark the runway, approach and taxiway lights are lit. High up there is the land and the sea under it, with coasts, towns and rivers, contrails, and the curve of the earth. With the ground pack, at any height, the land stands at its own height, its hills hiding what is behind them, in the colours of what covers it - see [The ground pack](#the-ground-pack).

| Camera | |
| --- | --- |
| CINEMA | Cuts by itself between shots made for what the aircraft is doing: a long lens up the approach, the touchdown from low beside the runway and a half-speed replay of the flare, the roll-out alongside and the taxi in from the tower; lined up, the take-off roll, the climb out and climbing away; chase, wide and from-below shots in turn when cruising; for a helicopter, a camera on the ground by where it sets down or lifts off. |
| CHASE | Behind it, a little above. |
| ORBIT | Round it; drag to turn the view. |
| TOWER | At an airport, from the control tower's cab - raised where a building would be in the way. |
| FLY PAST | A camera set down beside its path where it will be in about 7 seconds, the lens following it without zooming: small far off, growing as it comes, sweeping by side-on and shrinking away; set down ahead again on the other side. |

ZOOM IN and ZOOM OUT move the camera nearer or further, but for CINEMA's. SOUND turns the engines' noise on or off: made as it plays for each kind of engine - a fan's whine and the roar behind it, a turboprop's drone, a helicopter's chop - but for a fighter's roar, cut from recordings of real Eurofighter Typhoons by `tools/gen_roar.py`, its front ahead of it and its jet behind, played a stretch at a time from places picked at random so that it never comes round as a loop, at the pitch its flight puts on it: shaped noise, however its spectrum was set, was a gale on the Tab5's small speaker, which plays little under 300Hz. An airliner's, a turboprop's and a light aircraft's can be played from recordings too - each pass's Doppler shift taken out first, from the line it flew - to set against their synthesised voices by ear: `##e` on the serial port, each time the other. And its tyres, a screech from each main gear in turn as it touches down, its pitch falling as the wheels spin up and louder for a firmer landing, then the roll of rubber on concrete and the nose wheel's thump over each centreline light (`src/engine_noise.cpp`). The air tearing past it as well: dipole noise off its edges, its pressure going as the cube of the speed - a light rush off a clean wing, more off the flaps' edges, and most off the gear's legs and wheels once they are down, building over the seconds they take to come out - so that on an approach, the engines throttled back, the airframe is as loud as they are, as measurements of today's twins have it; and on the roll-out the spoilers' buffet, the air torn off the wing. At the stand, its engines shut down a minute after it parks - the fuel cut, the roar gone at once and the whine winding down over half a minute - and an airliner's APU whining in its tail, as on any apron; started as it is pushed back, the core's whine rising on the starter, the fire lit at a third of idle and the roar swelling in. Only what is heard outside it: the gear's down-locks knock in the cabin, not on the apron. The air carries it as it would. It is heard late, at 343m a second: what the aircraft was doing a moment ago, from where it was, its pitch raised by how fast it was coming then, so a flypast is seen before it is heard. It falls off with distance, and the air takes the treble first as ISO 9613-1 has it for 20°C and 70% humidity: a kilometre off, little above a kilohertz. It comes off the ground as well as straight, a little later and weaker, and the two add and cancel by turns up the spectrum, the sweep of a jet going by as the difference between the two ways changes; a runway gives nearly all of it back, grass less, and less of the treble. Far off it shimmers, as the air's eddies bend it. `tools/engine_preview` plays any of seventeen scenes on the PC and saves them as WAVs; the ground's notches come where the geometry puts them, to within one percent. The airport's clearances are spoken as they are in the zoom.

**HILLS**, under ZOOM OUT, is lit while the land is drawn at its height, from the ground pack - see [The ground pack](#the-ground-pack). A press switches the hills off: the land is flat, with the hills along the skyline, as without a pack, and the frames come quicker - a Cessna at Glasgow at about 45 a second rather than 27 - and another press brings them back. It is kept with the settings, on until it is switched off, and greyed - nothing to switch - with no pack, one the Tab5 refuses, or away from the land the pack covers, where the line under the picture says why the land is flat; switched off by choice, that line says nothing of it.

Aircraft are placed at their true heights: from the GNSS height a report gives, less the geoid, or else its pressure altitude put right by the day's pressure, worked out from the aircraft around that give both - the labels keep the pressure altitude every screen shows. On a day of low pressure the traffic used to stand a few hundred feet over the airfield, and a landing's last seconds came down as a dive onto the runway.

**In a replay** too: **3D**, under Export on the replay screen, opens the 3D view of the aircraft the recording was following, and moves on as the recording follows another; any other aircraft is a tap away, from **3D** on its details. The strip under the picture holds the replay's controls - Play or Pause, a minute back or on, 1x or 4x, and a bar to tap anywhere along - with the flight on a line above them, at the recording's time in UTC. The view runs on the recording's clock: paused, it stands still, the engines quiet and the camera free to turn; a jump starts the shot afresh. A replay's heights are put right by its own day's pressure, worked out from its recorded aircraft, not today's. Videos are made from the radar replay still: the 3D view draws straight to the panel, past the canvas the encoder reads.

Each frame is prepared on one of the P4's cores and drawn in bands on both, its inner loops in the P4's PIE vector instructions, and each band is turned into the portrait panel by the PPA while the next is drawn. It runs at about 20 to 55 frames a second with the hills, and 40 to 70 with them switched off.

### The airfield pack

The firmware knows every airport's runways, from OurAirports, and with those alone the 3D view at an airport is a basic one: the runways, their paint, lights and approach lights, and a line in amber under the picture saying why there is no more. The rest - taxiways and their centrelines, aprons and stands, holding points, buildings at their heights, windsocks and the control tower - is in `airfields.bin`, the airfield pack: 3,214 airfields from [OpenStreetMap](https://www.openstreetmap.org/copyright), 14.7MB, more than the firmware's flash has room for. It is on each release's Assets - v1.5.0's is [https://github.com/craigdianesmith-glitch/tab5-adsb-flight-tracker-cpp/releases/download/v1.5.0/airfields.bin](https://github.com/craigdianesmith-glitch/tab5-adsb-flight-tracker-cpp/releases/download/v1.5.0/airfields.bin); copied into an `overhead` folder at the top of a FAT32 microSD card, it is read an airport at a time as the 3D view opens there, in about a fifth of a second. With it, a followed aircraft taxis along the real taxiways to and from its runway, aircraft parked at a stand are shown on it, nose in, and the airport zoom marks the control tower. `tools/gen_airfields.py` builds it from the OpenStreetMap planet. The [user manual](https://github.com/craigdianesmith-glitch/tab5-adsb-flight-tracker-cpp/releases/download/v1.5.0/Overhead-v1.5.0-User-Manual.pdf), a PDF on the release, takes a beginner through putting it on a card.

### The ground pack

With `ground.bin`, the ground pack, also in the card's `overhead` folder, the 3D view draws the land at its height - its hills and mountains from any height, at an airfield, on the approach and en route over the round earth - and in what covers it: woods, fields, moor, towns, lochs and marsh, and bare rock, each cover's colour lit as the land is and shaded as the hills lie, from the light and shade of their slopes. The haze over it thickens quickly over the first 2km and slowly beyond, toward a horizon some 30km off, and the land is drawn as far as the haze lets anything be seen, 100km at most, the earth's curve taken off; an aircraft behind a hill is hidden by it. Both need the pack: without it, or with one the Tab5 refuses, the land is flat and one colour, with its towns and rivers, as it was in 1.5.0, and the line under the picture says why. With the pack, HILLS, among the 3D view's buttons, trades the hills for quicker frames, the land flat with the skyline. It is on each release's Assets, beside the airfield pack - v1.5.1's is [https://github.com/craigdianesmith-glitch/tab5-adsb-flight-tracker-cpp/releases/download/v1.5.1/ground.bin](https://github.com/craigdianesmith-glitch/tab5-adsb-flight-tracker-cpp/releases/download/v1.5.1/ground.bin), 27MB - and goes in the same `overhead` folder at the top of the FAT32 card, as `overhead/ground.bin`. The [user manual](https://github.com/craigdianesmith-glitch/tab5-adsb-flight-tracker-cpp/releases/download/v1.5.1/Overhead-v1.5.1-User-Manual.pdf) takes a beginner through putting it on a card and checking it worked.

What covers the land is [ESA WorldCover](https://esa-worldcover.org) 2021's ten-metre map, sampled sixteen times in each cell of the pack: a cell has the cover most of its samples have, or one of four mixes the map has no class for - a suburb, a fifth to three fifths of it built over, roofs among gardens and trees (which, at ten metres, the map mostly calls trees, so the leafier suburbs came out as woods); a town's middle, nine tenths built over or more, darker; moor, grass up where the hills' rough grazing is - above a line from 400m on the south coast to 150m in Shetland, ragged as a head dyke is, or on slopes steeper than 22 degrees - which the map calls grass, as it does the lowlands' pasture, so the Highlands came out the green of a lawn; and rocky ground, a fifth or more bare rock and scree. The hills' light and shade are the [Copernicus DEM](https://spacedata.copernicus.eu/collections/copernicus-digital-elevation-model) GLO-30's, their heights GLO-90's. `tools/gen_ground.py` reads them all straight from their open archives and makes the pack: tiles a fifth of a degree square, cells of 2.5 seconds of latitude - some 75m - kept near square by taking 1.5 to 3 times as many seconds of longitude further north, a byte a cell; each tile at five levels of detail, each a quarter of the one before, with heights every 15 seconds and at the coarsest level's cells. The UK and Ireland are 2,068 tiles and 27MB, made in 12 minutes, eight tiles read at a time. Every tile's coarsest level is read in as the view opens, half a megabyte for the whole country in under a second; the three next a tile at a time round wherever the view is, out to some 45km, in the background, nearest first; and the finest, the 75m cells, for the tiles round the eye.

The pack on each release covers the UK and Ireland; one for anywhere else is made on a computer by `tools/make_ground_pack.py` - see [A ground pack for your own country](#a-ground-pack-for-your-own-country). The Tab5 takes a pack only within what it can hold: at most 6,000 tiles - nearly three times the UK and Ireland's - their coarsest levels at most 4MB as it holds them, which below 50 degrees, where a tile's are bigger, comes first, at 4,315 tiles; and a grid of at most 40,000 places, the pack's rows by its columns of tiles, a tile in each or not, 22 bytes each. They are `MAX_TILES`, `MAX_COARSE_BYTES` and `MAX_GRID` in `include/ground_pack.h`, and the tool builds to the same. A pack past any of them, or for another version, or damaged - cut short, or its index pointing past the end of the file or a tile off its grid - is refused as the 3D view opens, from its header and index alone, before its tiles take any memory, and the land is drawn flat and one colour, as with no pack. So it is, too, where the pack has no tile anywhere round the eye, in the 11 by 15 tiles - some 245 by 210km - of the grid of heights the land is drawn from, and no grid is built: no march across noughts. Nearer the pack's edge the grid is built from the tiles there are, the land off the pack level at the sea's height - flat close by, and the pack's hills in the distance. The line under the picture says why the land is flat, as it says why an airport is the basic view - "Flat land - no ground.bin in the SD card's overhead folder", "Flat land - the card's ground.bin is too big for the Tab5: build a smaller one", "Flat land - here isn't in the card's ground.bin". Settings > About lists the packs on the card, under **On the SD card**: the ground pack's tiles, its size and the area it covers - `Ground pack: ground.bin, 2,068 tiles (25.7MB), between 49.8N and 61.0N, 10.8W and 2.0E.` for the release's - or why the 3D view can't use it, and what to do. And the serial log says it at start-up, beside the airfield pack's: `[ground] the card's ground.bin: 2068 tiles, 25.7MB`, or `[ground] the card's ground.bin is too big for the Tab5: 7012 tiles, the most 6000 - build it smaller (see the manual)`.

Close to, 75m cells are still big: from 1,000ft, a mile ahead, one is forty pixels across, and the land a patchwork of squares. So for the two by two tiles nearest the eye, the ground pack's task works out two levels finer still from the pack's finest - 37.5m and 18.75m - in the P4's spare time. Each of their cells has the cover of the pack's cell nearest a point moved off its own by a noise smooth over a cell or so, so that the edges of fields and woods and the shore wander as they do, rather than stepping by 75m; and its light and shade from between the pack's four nearest, so that the hills are smooth rather than faceted, roughened as its cover is - a wood's crowns and a town's roofs most, a field's a little, water's not at all - and dithered to the sixteen levels a cell has. The noises come from where each cell is in the world, so the land is the same each time it is worked out, and either side of where tiles meet. They are drawn as the pack's own levels are, for nothing more each frame.

Level ground - the rows that see nothing but an airfield's level ground, and all of the land while there are no heights to draw it at - is drawn a row at a time, each row a straight line across the pack's grid - worked out once a frame from the camera, or high up, on the curve of the earth, from five points along the row - at the finest level whose cells come to four pixels or more, a cell every four pixels, read for one row and kept for the row under it. The cells are read eight at a time with the P4's PIE instructions, their places in the tile worked out in vector lanes - 16 bits each, so the finer levels are kept in parts of 144 rows, as many as each needs - and written four pixels to an instruction. Where the near land's cells are tall and wide on the screen, the drawing does less for the same picture: one walk along the cells for four rows rather than two, where they are eight rows or more tall, and a sample every eight pixels rather than four, where they are sixteen or more wide, written eight pixels to a PIE store.

The land at its height is marched: a ray up each column of four pixels, out from the eye, over a grid of the land's heights that the ground pack's task builds round wherever the view is - 11 by 15 tiles, 48 rows by 32 columns of heights a tile, the pack's own every 15 seconds of latitude, some 460m, so that a hill smaller than that is smoothed away - built afresh as the eye moves on two tiles, and again as the tiles' finer heights come in, so that a new place's detail firms up over its first seconds; and each 8 by 8 of them with its highest, for whole blocks to be passed over. A ray's steps grow a fortieth each, half a cell at the least, out to 100km, or less where the haze leaves nothing to see - a quick rise in it over the first 2km, the damp air near the ground, and a slow one on toward a horizon some 30km off. Each sample is set against the line of sight, the earth's curve taken off, and one under the line through the last row filled is hidden, its height worked out only where it may show; a column is given up once the highest land about could no longer rise into view. At an airfield the ground is held level at the field's elevation out to 2.5km and eased into the land by 5km. A sample's colour is its cover's, at the finest level whose cells come to four pixels or more, two rows to a sample, lit and hazed. The march and the colours are hand-written RV32 assembly - `src/scene3d_march.S` and `src/scene3d_terrain.S` - with the C beside them as the reference, the bench drawing frames both ways to the same pixels. When frames run long - from 27ms, under 37 a second - the frame-rate governor has the land skimp, its steps growing by up to a twentieth, a whole cell at the least, out to 70km rather than 100, a sample every four rows; and gives it its detail back, slowly, under 23ms. HILLS switches the land at its height off altogether - see [The 3D view](#the-3d-view).

While the heights round a new place are being worked out - the second or two after the view opens there - or where the memory isn't free for them, or with HILLS switched off, the skyline stands in for the hills: the ground pack's task works out how high the land stands along each of 720 bearings round the eye, the highest anywhere from 5 to 100km off, and each frame those highest points in view are seen from where the eye is now, hazed as far off as each is, drawn down to the eye's horizon - none above 4,000m, where the hills are seen from above, nor where the eye is down among them.

The land at its height keeps its depth - a bfloat16 1/z, filled in between the samples perspective-correct - so that what is beyond a hill, an aircraft or a coast's pale line twenty miles off, is hidden behind it. And those pale lines, the coasts' and the lochs' shores, fade into the land's colour where they are seen low along it, as a beach is a hundredth of a pixel twenty miles off from 1,500ft; over the pack's cover they aren't drawn at all, its cells drawing land meeting water themselves - from other data, the line ran a kilometre out over the sea from the shore at Lossiemouth.

Measured on the Tab5, with the WiFi idle, with the hills and with HILLS off: a Cessna at Glasgow, about 27 frames a second against 45; an A320 coming into Heathrow, 31 against 46; a 767 at FL300, 32 against 47; a Typhoon over the Cheviots, 33 against 54.

#### A ground pack for your own country

The pack on each release is the UK and Ireland's. `tools/make_ground_pack.py` makes one for anywhere else, on a computer - Windows, a Mac or Linux - from the same open archives, read over the internet as it goes, nothing to download first: for a country, by its name or its code; for a state, province or region of one - Texas, Bavaria, Scotland, Lombardy; for several of them; for a circle round a town, or round a latitude and longitude; or for a box of latitude and longitude. Run with nothing after it, it asks where, says what the pack will take, and asks before it starts. The Tab5 reads one pack, `overhead/ground.bin`, so a pack of your own takes the place of the UK and Ireland's; to have both, name both in one pack, within the limits above. The user manual takes a beginner through it, from installing Python to the card.

Getting ready, once:

1. Install Python 3 from [python.org](https://www.python.org/downloads/). On Windows, tick **Add python.exe to PATH** on its first screen; on a Mac, run **Install Certificates.command**, in its folder under Applications, afterwards. On Linux, the system's `python3` does.
2. Download this project - **Code**, then **Download ZIP**, at the top of its GitHub page, or a release's **Source code (zip)** - and unzip it. (The three files the tool needs will do instead, in a folder of their own: `tools/make_ground_pack.py`, `tools/gen_ground.py`, which makes the tiles, and `tools/requirements.txt`.) Open a terminal in the `tools` folder: on Windows, click the folder's address bar in File Explorer, type `cmd` and press Enter; on a Mac, open Terminal, type `cd ` and drag the folder onto it, then press Enter.
3. Install the three add-ons to Python it needs - numpy, rasterio and Pillow, listed in `tools/requirements.txt`. On Windows: `py -m pip install -r requirements.txt`. On a Mac or Linux: `python3 -m venv ~/groundpack`, then `~/groundpack/bin/pip install -r requirements.txt` (on Debian or Ubuntu, `sudo apt install python3-venv` first).

Then make the pack: `py make_ground_pack.py` on Windows, `~/groundpack/bin/python make_ground_pack.py` on a Mac or Linux, and answer its questions - or say where after it:

```
py make_ground_pack.py Luxembourg
py make_ground_pack.py France Belgium
py make_ground_pack.py Texas
py make_ground_pack.py "Limburg, Belgium"
py make_ground_pack.py --around Zermatt --radius 25
py make_ground_pack.py --around 46.02,7.75 --radius 25
py make_ground_pack.py --list Germany
```

It makes the tiles the areas touch and some 30km round them (`--margin`), so the hills just over a border or across the water are there too; tiles of nothing but open sea are left out, the 3D view drawing the sea the same without them. A country's parts far from the rest - France's overseas regions, the Caribbean Netherlands, Hawaii - are left out and named, each to be made a pack of on its own. The moor - grass high up or steep - is the British Isles' hill grazing, so it is drawn on the tiles in and near them only, and grass is grass everywhere else (`--moor on` or `off` to choose). Where the GLO-30 isn't public - Armenia and Azerbaijan - the hills' light and shade come from the GLO-90 instead, and it says so. The tiles are `tools/gen_ground.py`'s own, which it imports: a box of latitude and longitude made by either is the same pack, byte for byte.

Before it starts it says how many tiles the pack will be, its size, the Tab5's memory for it and how long it will take; and it won't make one the Tab5 can't hold - past `MAX_TILES`, `MAX_COARSE_BYTES` or `MAX_GRID`, which in practice is a country the size of France, Germany, Spain or Sweden - saying instead how to make a smaller one: some of a country's regions, or `--around` your home with a `--radius` of up to some 600km. Each tile it makes is kept in a cache folder as it is done, so a build stopped - the connection dropped, the laptop closed, Ctrl+C - carries on where it stopped when the same command is run again; the pack is written to a temporary file, and renamed only once every tile is in. Beside the pack - `ground.bin`, unless `--out` names another - it writes `ground-NOTICE.txt`, the data's credits, to keep with the pack if it is passed on, and `ground-preview.png`, a picture of what it made: the land in the 3D view's colours, shaded by its hills, the areas chosen outlined. Last, it says what to do with the pack - onto the card's `overhead` folder as `ground.bin` - and the line Settings > About will show for it.

Luxembourg and the land 30km round it came to 84 tiles and 3.2MB, made in two minutes; 25km round Zermatt, 16 tiles and 1MB; Malta, 5 tiles and 49KB, 24 more of open sea left out; Switzerland and the land round it, 337 tiles and 18MB, in seven minutes - on a computer busy with other work, and so slower than they need be. On a quiet one a tile takes some two seconds for each 192 columns it has, three south of 50 degrees, eight made at a time, most of it reading WorldCover: the UK and Ireland's pack, twelve minutes. Every pack these made was taken by the firmware's own checks, `tools/ground_pack_test`, and drawn by the preview, `tools/landing3d_preview` - its enroute view over a pack's own country with `AT="lat lon"`.


## Alerts

Four kinds, each switched on or off under **Settings > Alerts & recording**:

- **Emergency** - squawking 7700, 7600 (radio failure) or 7500 (hijack).
- **Military** - a military aircraft passing through. A feed that doesn't mark them - adsb.fi's point endpoint - can't say which contacts are military, which is one reason Auto keeps going back to adsb.lol (see [Data sources](#data-sources)).
- **Watchlist** - entries typed on the keyboard, matched against callsigns, registrations (dashes optional, so `G-ABCD` and `GABCD` both work), type designators and ICAO hex codes. A three-letter entry is an airline: `RYR` matches every flight number that starts with it. Entries are letters, digits and dashes, 2 to 10 long, and a list holding anything else is refused with the offending entries named, rather than kept and never matched. A **long press** on a table row puts that flight's callsign on the list, or takes it off, and so does **WATCH** - **UNWATCH** for one on the list - beside FOLLOW on an aircraft's detail screen; either way its row turns amber, and an alert sounds at the next poll.
- **Rare type** - a short list of notable designators (the A380, 747s, the An-124, the Beluga, heavies and warbirds) plus readsb's own "interesting" flag where the feed carries it.

An alert puts a banner across the table, radar or detail screen - red for an emergency, amber otherwise - with what tripped it, the callsign, type and distance. Tap it for the aircraft's details, tap the X to close it, or leave it: it goes after 20 seconds. A three-note chime plays, or a two-tone warble for an emergency that can't be mistaken for it, and then a voice says what it is - "Emergency", "Watchlist", "Rare aircraft" or "Military", for the reason the banner names - spells out the callsign in the phonetic alphabet, and says the type as its maker and model: "Military... Romeo Charlie Hotel two one... Boeing... Charlie one seven". **While following**, an alert is its chime and its banner alone, with no words: they cut across the clearances and the engines of the aircraft being watched, with news of something else. The chime waits for a clearance or a reading being said to finish rather than cutting it short, and one kept waiting more than 8 seconds is dropped, its banner having said it by then. An emergency is still said in full. The callsign flashes red three times on the table and the radar, in step with the chime, then stays amber (red for an emergency) for as long as the aircraft is in range.

Each aircraft alerts once per sighting, and again only if it trips a new rule - a watchlisted airliner that then squawks 7700. An alerted aircraft is never trimmed off a busy radius: the poll keeps the nearest sixty contacts for the radar, and any alerted one beyond that is kept as well.

## Recording and replay

**REC**, on the radar and in the zoom, records whatever is on show - every contact, at every poll - to the SD card, and counts up while it runs: the radar around home; the radar centred on a followed aircraft; an airport's zoom, with or without one followed in it - each poll marked with which, and who answered it, so a replay shows each the way it was seen, switching between them as the screens did. Started by hand it runs until REC is tapped again, through following or not, and while following says who in the list. With **auto-record** on, an alert starts one, and it runs for as long as any alerted aircraft is in range and a minute after the last has gone, so a contact that drops out for a poll or two doesn't split one sighting into several files. Stopping an auto recording by hand holds it off until those aircraft have gone, or the next poll would start another. Changing the location, range or traffic filter stops a recording, since its header holds the home and range its plot is drawn around. Following an aircraft starts one too, stopped by its own rule - see *Follow me* above.

Recordings are plain text in `/overhead`, named by the UTC time they started - a short header, then for each poll an `F` line and an `A` line per aircraft (a following recording adds a `follow` line to the header, naming the aircraft, and the view to each `F` line: `-` for the radar centred on it, or the airport code of a zoom; and where **ZOOM IN** had the radar around home or a zoom closer in than its own range, the range shown follows the provider, in nm, for replays and their videos to show it at that range - and a zoom zoomed in on an aircraft followed, centred on it, as it was live) ; and where the live zoom had lately seen runway ends in use, a `runways` line naming the airport, each end and how many seconds before - `runways GLA 23 412` - so a replay's zoom starts out knowing which way the airport was working, as the live zoom did, rather than only once something lines up in the recording) - so a card pulled from the device can be read on a laptop. At about 90 bytes per aircraft per poll, a quiet civil sky is about 0.2MB an hour and a busy military one at 15-second polls about 1.3MB. Each poll is flushed as it is written, so a card pulled or a battery run flat loses at most the poll in progress.

A recording carries on in a new file - its next part - every 4 hours or 4MB, whichever comes first. Opening one reads all of it to index it, at about 1MB a second, so the cap is on size: no part takes more than about five seconds to open, and a progress bar shows across its row while it does.

The card is write-tested at boot - written, read back and deleted - since a locked or failing card mounts happily and then loses every recording. Without a usable one, REC, Replays and the auto-record switch are greyed out; a tap on either button has another look for one, as does auto-record whenever an alert would start a recording.

**Replays** is a button in three places - the table's header, an arrow round a play triangle beside the radar's icon, and the radar's and the airport zoom's button columns, under REC - and its Back goes back to whichever it was opened from. It used to be on the radar alone, which was two taps from the table, and three once the radar had been left on an airport's zoom, which is where it comes back to. From the zoom, the zoom is left as its own Back leaves it and opened again on the way back, unless something is being followed, when it is the radar centred on that. The header's opens the list with or without a card, since the list says when there is none; the other two are greyed out without one, with REC. It lists recordings newest first, seven to a page, with what started each, its range and size, and which speeds it has been exported at. A delete takes two taps, and takes the recording's videos with it - which it says before the second. Playback draws the plot as it is live, with ten-minute trails - unless **replay tracks** is off on the display page - each contact gliding between polls rather than jumping; play and pause, a minute either way, a bar to tap anywhere along, and 1x, 4x, 16x or 64x. A tap on a blip opens that aircraft's details as they were at that moment, with **3D** on them to watch it in the 3D view; **3D** under Export does the same for the aircraft the recording follows (see [The 3D view](#the-3d-view)).

## Video export

**Export** on the replay screen renders the whole recording, at the speed chosen, to an MP4 - H.264, 1280x720, ten frames a second - in `/videos` at the top of the card, named after the recording and the speed (`20261002-143155-16x.mp4`). The video is the replay as it looks on screen without the buttons, with the speed in the header. While it runs, the panel shows progress, the time left and Cancel, and the screen shows the frames as they are made. Once a recording has a video at the chosen speed, Export is greyed out and reads *Exported*; another speed is another video.

Each frame is drawn into the canvas, converted by the PPA into the encoder's YUV layout, encoded by the P4's hardware H.264 block, and written by a small MP4 writer (`src/mp4_writer.cpp`): the encoder hands back Annex-B, NAL units behind start codes with the SPS and PPS in front of every keyframe, and MP4 wants each NAL behind its length and the parameter sets once, in the track's sample description, with the index of frame sizes written last. A keyframe every three seconds keeps it seekable. It comes to about 230kbps for a radar scene, so about 1.7MB a minute.

Measured exporting a 90-second video (903 frames):

| | first version | now |
| --- | --- | --- |
| export, start to saved | 78s | 48s |
| colour conversion, per frame | 41ms | 28ms |

Two changes made the difference. Only what has changed since a buffer last held a frame is converted - on a replay the title, the panel's labels and the frame of the plot never move. That needs a list of changed regions kept apart from the flush's, since the flush merges neighbours in a band into one strip, which for this joined the panel, the plot and the footer into nearly the whole screen. And encoding and writing run on a task of their own on core 0, from one of two buffers while the next frame is drawn and converted into the other. Every frame of the faster export decodes identical to the slower one's.

## Sharing over WiFi

**Share** on the Replays screen serves a page of the card's videos and recordings to anything on the same network, and puts up a QR code a phone's camera opens it from, along with the address and `http://overhead.local/`. Videos play in the browser, download and delete; recordings download.

The server answers byte-range requests - Safari won't play a video from one that can't - and writes its own headers so a file goes with its length rather than chunked. It runs on its own task on core 0, reading the card 16KB at a time under the recorder's lock, so the table stays live and a recording carries on while a phone downloads, at about 1.3MB a second. File names from a URL are refused rather than cleaned up unless they are names this device would write, and only videos can be deleted.

There is no password, so it runs only while the share screen is up, and Back stops it.

## Splash screen

At boot, while WiFi joins, a title screen: a runway running off to a dusk horizon with the sun going down beside it, and **OVERHEAD** across the sky, with the version in the corner. An airliner, nose on, rolls down the runway from a speck at its far end, lifts off with its landing lights blazing, tucks its gear up, and comes on ever faster - in perspective, the runway's own - until it fills the screen and roars out over the top of it: overhead. It plays for three seconds to a jet taking off, and stays up with "Connecting to ..." under it if the network takes longer, for the rest of the 15 seconds boot waits on it. All of it is drawn - polygons into the canvas, no images - by `src/splash.cpp`; the scene is drawn once and kept, and each frame only puts it back where the plane was and pushes the patch the plane moved through, so it runs at 55-60 frames a second where redrawing the whole screen managed 11. The take-off is synthesised by `tools/gen_jet.py` from noise and a sine - a roar opening out as the engines spool up, the turbines' whine climbing over it, the crackle of the exhaust at full power, and then the roar closing and the whine dropping as it climbs away - 3.6 seconds at 16kHz, 112KB of flash. Muted, it plays silently.

## Sound

A jet taking off with the splash screen at boot (below), and a short blip whenever an aircraft that wasn't there before appears in the table - one blip per poll however many arrived, and never on the first poll after a start or a location change, where every aircraft is new by definition.

Every tap clicks, as a phone's keys do - a key, a button, a row, a heading, a switch - as it completes, which is when all but the radar and the zoom act on one, so scrolling the table or dragging a slider doesn't; on the radar and the zoom as it lands, unless it starts a drag across the plot. Holding a table row clicks again as the hold takes. Rather than the beep the keyboard alone used to make, it is 35ms of a key's snap - noise filtered to around 5kHz, gone in a millisecond - over a short, dry knock that rings and dies away, its partials at 2.2 and 4.6kHz: a bright Android-like tick, picked over a woodier iPhone-like tock (`--style tock`), and pitched high either way since the Tab5's speaker has nothing much below 300Hz for a thud. It is made by `tools/gen_click.py`, 1.5KB of flash played as the words are, on a channel of its own that cuts off the click before it, so fast typing doesn't queue up behind itself or behind an arrival blip.

An alert plays a rising three-note chime, or a two-tone warble for an emergency, on a channel of its own, a note at a time from the main loop so it never holds up the screen - and then the word for what it is, and the callsign a letter or digit at a time, a moment's pause after the word and a shorter one between letters. The type is its maker, then its model spelt - the first word of its name with a digit in it, up to a variant after a hyphen, so an A380-800 is "Airbus... Alpha three eight zero" and a C-130J "Lockheed... Charlie one three zero Juliet" - and then neo, MAX or Dreamliner where the name has one; a type the table doesn't know isn't said. The words are recordings in flash - the four reasons, the 26 letters of the phonetic alphabet and the ten digits, niner among them, the 46 makers in the type table and the three variants, for the zoom's announcements below the 46 airlines and six words of clearance, and for reading aloud the 27 words of heights, speeds, headings, navaids and frequencies - half a second to a second of sound each at 16kHz, squeezed as broadcast speech is so a word is as loud as the chime before it, turned back into samples as it is said - a millisecond for a second of word, into one of two small buffers in PSRAM in turn - and played by the speaker's own task, so saying one costs no more of the UI's time than a note: the main loop only hands the speaker the next once the last has finished. **There are three voices**, and what is said about somewhere is said in its own: Scotland's in a Scottish voice, England's in an English one, the United States' in an American one, and everywhere else's in whichever of the three is picked on the alerts screen - Scottish to begin with. An alert is in the voice of where the aircraft is, a clearance in that of the airport it is at, a card in that of its navaid or airport - wherever the device is, so a zoom opened on JFK from Glasgow speaks American. Where somewhere is comes from `tools/gen_regions.py` (`src/regions.cpp`): each airport in the table placed in Scotland, England or the United States ahead of time against Natural Earth's map units at full detail, an airport at the water's edge - a few hundred metres off Natural Earth's coast - going to the country whose land is nearest, within 5nm; and an aircraft taken to be where the nearest airport within 40nm is, which puts one over the Firth of Clyde in Scotland and one off JFK in the United States, or failing that inside whichever outline it is in, kept to a couple of kilometres (37KB). The voices are 16kHz rather than their own 22.05kHz - resampled by a Kaiser-windowed sinc, a quarter less flash for speech the Tab5's small speaker plays no differently - and stored as 4-bit IMA ADPCM, a quarter of 16-bit samples and half of the 8-bit ones they were until 1.4.1. The standard encoder put 20 to 23dB of signal over the noise it added on words squeezed as these are, which are full of the sharp edges ADPCM follows worst; `tools/adpcm_search.c` chooses each sample's four bits for the least error over it and the next two rather than for the nearest alone, which made it 26 to 28dB, for the same decoder. 193 words each: 1.15MB Scottish, 1.24MB English and 1.36MB American, the American the slowest speaker - 3.7MB less flash than as 8-bit, out of 14.7MB. The words that were chosen by ear were converted as they were, by `tools/voice_adpcm.py`, rather than spoken again: Piper says a word a little differently each time. They are made by `tools/gen_voice.py` with [Piper](https://github.com/rhasspy/piper), an offline neural text-to-speech engine, in its `en_GB-alba-medium` voice - built from the [CSTR, University of Edinburgh](https://datashare.ed.ac.uk/handle/10283/3270) Alba data, CC BY 4.0 - `en_GB-cori-medium`, from public-domain LibriVox recordings, and `en_US-amy-medium`, from Mycroft AI's [Mimic 3 voices](https://github.com/MycroftAI/mimic3-voices), CC BY-SA 4.0; another voice, or other words, is a run of the script away, which writes IMA ADPCM through the same encoder. Over USB serial, `##E`, `##W`, `##R` or `##M` sounds an alert of each kind for a made-up callsign and type at home, to hear one without waiting for it; `##C`, `##G` and `##U` an alert, a landing and an aircraft's details at Glasgow, Heathrow and JFK, in each of the three voices, and `##N` and `##A` then read the card of the navaid nearest there and of its airport.

The **airport zoom announces** each take-off and landing at its airport, while it is on screen, as a controller would clear it: "easyJet five three Tango Hotel, runway two three, cleared for take-off", or "...cleared to land". The airline is said by its name - every one in the airline table has a clip, with the rest of the callsign spelt after it; one it doesn't know has the whole callsign spelt - and the runway a digit at a time, with left, right or centre. They come from the runway simulation above: a take-off as the aircraft lines up or starts its roll, a landing as it is established on final, under 2,500ft and within 8nm. Each aircraft is announced once - not again for the same within five minutes, so a landing the simulation loses for a poll and picks up is one landing. Announcements have no chime, and wait behind an alert or each other, three at most, and one that has waited more than 8 seconds is dropped rather than said late; an alert that fires during one cuts it short - but while following, when an alert is its chime alone, the chime waits for it instead - and mute silences both. A clearance is only said while it still could be: for take-off while the aircraft is still on the ground, to land while it is still in the air - the simulation can be into a take-off by the time the zoom's next list has it, begun from the main poll's, and keeps it up to 1500ft. Alerts are said as before: the reason, the callsign spelt, the type. Over serial, `##T` and `##L` say a made-up take-off and landing.

An aircraft's details show its **route**, where [adsbdb](https://www.adsbdb.com) knows its flight number: the two airports' codes in a ROUTE row, as buttons - `[GLA] > [AGP]` - each opening that airport's zoom, with its own traffic fetched around it however far away it is, its Back coming back to the details, and its ZOOM OUT bringing up the radar around that airport, as if dragged there; in place of the size category the transponder sends, which said little - and their towns in the footer, `Geneva to London`, looked up as the details open by a task of its own, so the screen doesn't wait, says `looking up...` until it has it, and kept for the next time. It is crowd-sourced, so now and then wrong; a registration or a hex, which an aircraft without a callsign goes by, isn't asked about. An aircraft's details have **SAY** beside WATCH and FOLLOW, to hear them read out there and then, whatever the setting below. **Read aloud**, a switch on the alerts screen under the alerts themselves, says an aircraft's details as they open - "Ryanair six six eight Tango, Boeing seven three seven max, climbing, four thousand four hundred feet, one seven five knots, heading two four zero" - its height as a controller gives it: in thousands and hundreds of feet below the transition altitude, 18,000ft over the United States and 6,000ft, the most common in the UK, everywhere else, and as a flight level above it, "flight level three five zero"; and "on the ground" for one that is. And a navaid's card as it opens, "Golf Oscar Whiskey, V O R D M E, one one five decimal four" - a TACAN's channel, "channel one zero one X-ray" - and an airport's, a single set of the frequencies its card lists - one for each use, the first where a busy airport has several, as Heathrow has three towers and four ATIS: "Tower, one one eight decimal five; Ground, one two one decimal seven..." - an 8.33kHz channel's three decimals said. Each in the voice of where it is. A reading waits for an alert or a clearance being said, and for clearances waiting, which go stale in seconds - but cuts short a reading before it, and stops when its card or the details close. Under the switch, the voice for countries without their own, which says "Runway two three, cleared for take-off" as it is picked.

If the speaker goes quiet - no take-off at boot, no alerts, though each alert's `[sound]` line in the serial log says it was played - the Tab5's audio chip has stuck: a reset or a reflash restarts only the processor, and it takes powering the Tab5 right off, battery and USB, to bring it back. What sets it off isn't known: the once it happened, the Tab5 had been running on USB with its battery out.

The speaker icon in the header mutes it, and the setting persists. Muting silences the beeps rather than shutting the speaker down, so unmuting needs no re-initialisation - and unmuting plays the arrival blip, which is the one confirmation that can only be given in the medium being switched back on. `SOUND_ENABLED` and `SOUND_VOLUME` in `include/config.h` remain the build-time "never make a sound" and the level.

## Rendering

Everything draws into one shared landscape 1280x720 canvas in PSRAM, never straight to the panel. Drawing there is unrotated, so it's ordinary memcpy work. Each draw marks the region it touched, and `screen::flush()` hands just those regions to the PPA, which rotates them into the panel's framebuffer by DMA.

Measured on hardware (`-DRENDER_PROFILE` in `platformio.ini` logs the per-flush times):

| | before | after |
| --- | --- | --- |
| live data refresh | 650ms | 5-16ms |
| keypress on the location screen | 650ms | <1ms |
| full-screen repaint (boot, screen change) | 650ms | 42ms |
| clearing the canvas | 42ms (CPU) | 5ms (PPA fill) |

One thing that was tried and rejected: queueing the rects as `PPA_TRANS_MODE_NON_BLOCKING` and waiting only on the last, so the CPU fills the queue instead of making a round trip per transfer. Normalised against the work each flush actually did, it measured *slower* - 16.8us per KB against 12.5 - so the transfers are not waiting on the CPU, and the queue plus the completion interrupt cost more than the round trip they replaced. The blit stays blocking. What did come out of that attempt is worth keeping: `ppa_do_scale_rotate_mirror`'s return value is now checked, where a failure used to pass silently and leave that region of the panel showing the previous frame.

Two details worth knowing if you touch `screen.cpp`: the PPA's RGB565 byte order is the opposite of the one LovyanGFX uses for this panel (hence `byte_swap` on every blit, and the pre-swapped fill colour, both checked against what LovyanGFX itself reads back), and the canvas has to be flushed out of the CPU cache before the PPA's DMA can see it.

That cache flush used to be the floor under every push. `esp_cache_msync` is a range operation - it becomes `Cache_WriteBack_Addr(vaddr, size)`, run over both the L1 D-cache and L2 - so its cost follows the range it is given, and flushing all 1.8MB of the canvas cost the same whether the transfer that followed was the whole screen or one cell. With a 128KB L2 (`CONFIG_CACHE_L2_CACHE_SIZE`) at most ~2,000 lines of that canvas can be dirty, yet the sync was walking 28,800 lines' worth of addresses.

`flush()` now writes back only the rows its dirty rects cover, merged so cells sharing a table row sync once between them. A canvas row is 2560 bytes - a whole number of 64-byte cache lines - so every span is naturally aligned. Measured over ~100s of live traffic with `-DRENDER_PROFILE`:

| | before | after |
| --- | --- | --- |
| smallest flush | 4.07ms | 0.69ms |
| median flush | 9.19ms | 7.17ms (table) / 0.96ms (status line) |

The floor is what moved: a small update no longer pays for the whole canvas. A refresh that touches cells across eight table rows still syncs most of it, and there the PPA transfer dominates anyway.

This is only safe because of an invariant the screens already keep: every canvas write is covered by the dirty list at the flush that follows it - a partial redraw marks the region it touched, a full repaint goes through `clear()`, which marks the lot. Rows outside the list were therefore written back by an earlier flush and are already clean in PSRAM, which is also what lets the merged bounding-box blit stay correct. A screen that drew without marking would now show stale pixels rather than merely wasting a sync, so keep marking.

The poll task also trims each result set, nearest first, to the sixty contacts the radar will plot - a 60nm radius over a busy area returns well over a hundred aircraft, and carrying the long tail through a vector copy per refresh bought nothing. The cap is the radar's rather than the table's, since the table draws only the eleven rows that fit but the radar plots the lot; the result is published by `std::move`, so the only copy left per refresh is the one `loop()` takes to render from. Trimming in the poll task rather than at draw time also keeps "new arrival" meaning a new *row*, rather than beeping at every aircraft that enters the radius unseen.

The per-cell diffing earns its keep twice over: a cell whose value hasn't moved is never redrawn, and the cells that *have* moved are shaded for two seconds so a change is visible without having to watch for it. That costs one extra flush per poll - about 24ms in every 10 seconds, or a quarter of one percent of the time. `CELL_HIGHLIGHT_MS` in `include/config.h` sets how long the shading lasts, and the *Show flight refresh* toggle on the settings screen turns it off.

A full repaint of the table, returning to it from another screen, draws in 33ms and pushes in 42ms. The drawing used to be 44ms, half of it filling cell backgrounds that `clear()` had just filled with the same colour - narrow rects are slow to write into a canvas in PSRAM. A cell with no cached value is now known to be background already and gets only its border and text. A cell being redrawn is filled inside its border rather than over it, so the border is drawn once rather than on every refresh. A per-poll refresh is bound by the push rather than the drawing: an update of four columns across eleven rows takes ~17ms, and taking the border redraws out of it saved only half a millisecond - the bulk is the PPA rotating those rows into the panel, which already runs at its maximum burst length.

Rendering also means a refresh where nothing changed costs nothing at all, and the three screens share the one canvas rather than holding 1.8MB each.

### Where the time goes

Measured on the device in 1.4.1, with a benchmark build made for the purpose:

| | MB/s |
| --- | --- |
| CPU copying internal RAM | 550 |
| PPA filling PSRAM | 355 |
| DMA (AXI GDMA) copying PSRAM to PSRAM | 97 |
| CPU reading PSRAM | 93 |
| CPU writing PSRAM | 67 |
| PPA copying PSRAM to PSRAM - rotated or not | 44 |
| CPU copying PSRAM to PSRAM | 43 |
| CPU reading flash | 28 |

The push to the panel is bound by PSRAM, which the panel itself is reading from at some 120MB/s, sixty-odd times a second, all the while: the PPA rotates a full screen in 42ms, the same as it copies one unrotated, and no faster than the CPU copies one. Rotating it on the CPU instead - checked pixel for pixel against the PPA - took 62ms on one core and 53ms on both, of which only 20ms was the arithmetic, the rest waiting on PSRAM; so no hand-written or SIMD code could do better than tie with the PPA, and it would have the CPU to itself while it did. The screen push is as fast as this board's memory lets it be.

Left to itself, the radar leaves both cores nearly idle. Most of a frame was the push and the traffic, and both have come down. The traffic is drawn straight into the canvas's pixels - blips, vectors, chevrons, rings and labels - by the canvas's own algorithms, ported line for line from LovyanGFX so the pixels are the same, without a call through it for each: 18.4ms to 10.5ms for 120 aircraft, with a label's pick-list text built only when a list needs it. And a refresh in which only the traffic has moved pushes only the places it was and is - see below. A refresh of the live radar is now 7 to 9ms and of the zoom 8ms, against 40 and 44 drawn whole; twenty aircraft moving across the radar, 13ms. That makes frames between polls cheap enough to come as often as the fastest contact on the plot moves a pixel, so the traffic glides rather than steps, for well under a hundredth of a core most of the time. No view spends more than a quarter of the time drawing, so frames that have to be drawn whole - a crowd, or the zoom centred on an aircraft followed - are spaced out to suit. Of what is left, most is the touch chip, read over I2C at a quarter of a millisecond a time; it is read every pass while a finger is down and every other pass while none was, which halved that. A full redraw, arriving at the radar, is some 80ms, half of it the push; ZOOM IN and OUT, which change only the plot, the title and their buttons, refresh those rather than drawing and pushing the whole screen, which took them from 75-85ms to 48-64ms.

**A refresh of the traffic alone.** The radar and the zoom keep a copy of their plot without its traffic - map, rings, airports, navaids and runways, another 1MB of PSRAM - taken on the second full draw of a view, so a tap's own redraw isn't slowed by the copy, and kept for as long as the view is the same. A refresh in which only the traffic has moved puts back what the copy has under each box the last frame's traffic covered, draws the traffic where it is now, and pushes those boxes alone: one for each blip with its chevrons and ring, one for its label, and its vector in pieces along it, so a long one on a slant isn't pushed as the empty square round it. Boxes are pushed as one only where that is quicker, a push being 0.085ms and 53ns a pixel. The map's names are left out of the copy and drawn again into each box put back, as where they go moves with the traffic's labels; the runway ends in use, which move with the traffic too, are part of what makes a view the same. Past fifty aircraft or so, where putting back and pushing the boxes would cost more than the whole, the plot is drawn whole and the copy kept. Every kind of refresh in part was checked pixel for pixel against the same sky drawn whole, map and names on: twenty aircraft and 120, close in and far out, the names moved by the labels under a copy kept, and in the zoom.

Pushing those boxes turned up a slip that had been holding every such refresh back: the alert banner is registered with the screen once, at start-up, showing or not, and the push of a set of boxes took that as a reason to go the careful way round - every time, merged into one box nearly the size of the plot. Only boxes under the banner's strip go that way now, and the cache is written back once for all the rest, rather than a call a row: 0.3ms against 2.5. With twenty aircraft moving across the radar, a refresh in part went from 17ms to 13ms; with a dozen fast ones close in across the zoom, whose long vectors had made every frame one drawn whole, from 43ms to 20ms.

**The 3D view's own assembly.** Its innermost loops were each set against GCC's code for them, instruction by instruction, and timed on the device, the pixels compared. Contrails and blades' blur, tinting what is behind them, went from some 85 cycles a pixel in C to 22 with PIE, every span eight pixels at a time, its edges masked off: 7.6ms of a cruise's frame to 2.1, and the cruise from 48 frames a second to 62. A solid triangle's rows are drawn as two trapezoids, their edges stepped in fixed point, rather than in float a row at a time. The ground's triangles keep their colour while the haze doesn't change, rather than working it out again for every row. Each row's colours are multiplied by 1/255 rather than divided by 255, a float divide a channel: a quarter off working out the rows. Two things made no difference and were let be: hand-written assembly for the cover's cells one at a time, which ran no faster than GCC's, both held up on memory - eight at a time with PIE did go faster - and the cover's code in the chip's own memory rather than flash, which changed nothing and would have cost 40KB of it. The P4's cycle counters are exact on both cores, busy or waiting on PSRAM, which reads a 64-byte line in some 220 cycles.

**The engine noise.** Made as it plays, at 16,000 samples a second, on the core that also prepares the 3D view's frames. Its loop was calling out to a function three times a sample for the whines, and to `floorf` as each phase came round; written in line, and the phase wrapped with one conversion: a turbofan's 40ms of sound from 1.23ms to 1.07ms to make, 2.7% of a core alone and some 4% while the 3D view draws, the sound the same - byte for byte on the PC, and on the device but for where the compiler fuses a multiply and an add, which rounds the last bit differently.

The one part of drawing bound by the CPU rather than by memory was the map's first draw - see the map, under the radar - which went from some 200 cycles a point to being held up on memory, for 4.7 times as fast at 2000nm; and the names, which are kept from one draw to the next. Each change was measured against the code it replaced, and the map's checked pixel for pixel.

## Data sources

Live aircraft come from two providers, either of which can serve the whole app:

- [adsb.lol](https://adsb.lol), whose data is made available under the [Open Database License 1.0](https://opendatacommons.org/licenses/odbl/1-0/).
- [adsb.fi](https://adsb.fi), whose open data API is free to use without a key, for personal and non-commercial use, and asks that adsb.fi be cited with a link to its home page - which this is.

The firmware carries none of that data - it is fetched at runtime and displayed - so what appears on screen is an ODbL Produced Work, and the attribution is the obligation that comes with it.

### Why there are two

adsb.lol spent an evening answering `200 OK` with an empty aircraft array. Its API was up and its responses were well-formed; the feed behind it had drained, and its own `/0/me` reported `global.aircraft: 0` while `/v2/all` returned 503. Sampled at 8-second intervals, the point endpoint returned nothing for about eighty seconds and then refilled, cycling:

```
22:00:57  lol_point=0   lol_global=0       lol_all=503  | fi_point=6
   ...     (nine consecutive polls, total: 0)
22:02:22  lol_point=4   lol_global=3690    lol_all=503  | fi_point=6
22:02:39  lol_point=5   lol_global=10726   lol_all=503  | fi_point=6
```

At the point of parsing, that is indistinguishable from an empty sky - which is exactly what the table said, for several polls in a row. A failed request would have left the last known data up (see below); only a *successful* empty response produces "No aircraft in range".

So a single source is a single point of failure that fails silently, and **Auto** does something about it:

- Sticky, not round-robin: whichever provider last answered is asked first, so one that has gone down doesn't cost a 12-second timeout on every poll for the duration of the outage. But not for good: off adsb.lol, it is asked first again every five minutes. It is the one whose feed marks military and "interesting" airframes, so a fallback that stuck after a single 429 quietly switched those alerts off for as long as the device stayed up.
- A provider that fails outright is skipped to the next one.
- An empty result that follows a *non-empty* one is checked against the other provider before it reaches the screen. If that one finds traffic, it takes over and says so in the header. If both agree the sky is empty, it is empty.
- Only on that transition, so a genuinely quiet sky costs one request per poll rather than two.

### What a source has to describe

A source is a pair of endpoints rather than a URL, because providers disagree about more than their hostname:

| | adsb.lol | adsb.fi |
| --- | --- | --- |
| civil endpoint | `/v2/point/{lat}/{lon}/{radius}` | `/v2/lat/{lat}/lon/{lon}/dist/{radius}` |
| military endpoint | the same point query | `/v2/mil`, global |
| array key | `ac` | `aircraft` (point), `ac` (mil) |
| carries `dbFlags` | yes | no (point), yes (mil) |

Which is why `include/config.h` holds a table of `AdsbProvider` rather than a format string, and why each endpoint carries its own array key: adsb.fi's two really are differently shaped, not one path with a variant.

Where an endpoint omits `dbFlags` there is nothing to test, so the endpoint itself is the answer - everything from a military feed is military, nothing from a civil one is. And a *global* endpoint hasn't applied the radius, so the client does: it drops anything outside it, and anything it cannot place at all. That last part matters more than it sounds. adsb.fi's military feed carried 232 aircraft when this was written, 50 of them with no `lat`/`lon` at all; without that rule every one would have landed in a table captioned as showing traffic within a few dozen miles.

The URL templates use `{lat}`/`{lon}`/`{radius}` substitution rather than printf formatting. A format string that reaches `snprintf` from anywhere but a literal is how a `double` gets read as a pointer, and these are data - a mis-spelled placeholder can only ever produce a wrong URL.

### Paid alternatives, and why there are none here

Worth recording, since it looks like the obvious fix and isn't. A paid tier buys quota, not uptime, and the quota on offer doesn't fit a device that polls around the clock: 30-second polling is ~86,400 requests a month, where ADS-B Exchange's $10 Community tier allows 10,000 - about one poll every four minutes. [OpenSky](https://opensky-network.org)'s free tier is generous enough (4,000 credits a day, 1 per small bounding box, so a poll every 21s) but its state vectors carry no type designator and no military flag, which would empty the TYPE column and the military filter outright. [airplanes.live](https://airplanes.live) is the same readsb schema *with* `dbFlags` and would be a genuine drop-in, but its public endpoint currently answers 403 and asks you to get in touch first.

The reliable answer, if this ever needs one, is not a subscription but a receiver: an RTL-SDR running readsb on the same network serves `aircraft.json` in this exact schema with no rate limit, no TLS and no outages.

That endpoint is free, volunteer-run infrastructure, and the default refresh interval is set with that in mind rather than at the fastest the hardware or the dial would allow. `DEFAULT_POLL_INTERVAL_S` is 30 seconds: an aircraft covers perhaps three miles in that time, which at these ranges moves a blip by a few pixels, so the cost to the display is slight and the cost to the server is a third of what ten seconds asks of it. The dial is there for anyone who wants it faster on their own account - what matters is that every device doesn't take that by default.

`POLL_INTERVAL_MIN_S` stops the slider going below five seconds, and either provider answers `429` well before that if it has had enough - adsb.fi documents a limit of one request per second; a poll that collects one is followed by a minute's silence from that provider rather than more of the same. If you are flashing this onto several devices, leave them slower still.
